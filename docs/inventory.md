# Рюкзак и экипировка персонажа

Проект [показа вещи в чате](chat.md#показ-вещи) предусматривает публичный
снимок экземпляра через application-сервис inventory. Это будущий сценарий:
сейчас такой команды нет. Формирование снимка должно проверять владельца,
не перемещать и не резервировать вещь; вложение открывается без команд
инвентаря. Возможный обмен должен остаться отдельным подтверждаемым сценарием,
который заново проверяет имущество и меняет его через `InventoryService`.

Модуль `inventory` владеет PostgreSQL-таблицами `inventories`, `item_instances`
и `inventory_operations`. Владелец инвентаря — конкретный персонаж:
`InventoryContainer.ownerId` и `ItemInstance.ownerId` равны его `Character.id`.
У каждого персонажа один основной рюкзак и отдельные слоты надетых предметов.
Дополнительные контейнеры остаются совместимостью для ранее сохранённых данных;
основной интерфейс не должен предлагать создание новых инвентарей.
Все операции выполняются через `InventoryService`, хранение — через
порт `InventoryRepository`. Очередь не участвует в изменении имущества.

## Базовые операции

| Операция | Наблюдаемый результат |
| --- | --- |
| Получить | Чтение инвентарей, экземпляра, описания и доступных действий |
| Получить в награду (`receive`) | Сервер создаёт экземпляры определения у владельца; количество разбивается по лимиту стэка |
| Удалить | Уничтожить выбранное положительное количество; пустой экземпляр удаляется |
| Перенести | Переместить количество между контейнерами, включая контейнеры другого персонажа |
| Положить | Поместить принадлежащий персонажу экземпляр из состояния вне инвентаря в контейнер |
| Убрать | Сохранить экземпляр и владельца, установив `inventoryId: null`; это не удаление и не выбрасывание в мир |
| Разделить стэк | Сохранить исходный экземпляр с остатком и создать второй с новым UUID |
| Объединить стэки | Одинаковое определение в одном контейнере; сумма не превышает `stackLimit` |
| Создать инвентарь (совместимость API) | Создать дополнительный контейнер владельца |

При полном переносе сохраняется UUID экземпляра. При частичном переносе остаток
сохраняет исходный UUID, перемещённая часть получает новый. Между владельцами
меняются и `ownerId`, и контейнер. Упаковывание и перенос не создают имущество.
Объединение выполняется явно, автоматического слияния при переносе нет.

Основной рюкзак имеет 50 мест, каждое место — один ненадетый экземпляр/стэк.
Надетый предмет не занимает ячейку рюкзака и не должен отображаться в его сетке.
Надевание из рюкзака освобождает ячейку. Снятие должно возвращать предмет
в рюкзак; при отсутствии места операция отклоняется без изменения экипировки.
Надевание в занятый слот должно одной операцией менять вещи местами:
прежняя вещь возвращается в рюкзак, новая надевается. Замена доступна даже
при полном рюкзаке, поскольку число занятых ячеек не растёт.
Пока персонаж участвует хотя бы в одном бою со статусом `active`, надевание,
замена и снятие экипировки запрещены. Правило действует на всех ходах,
для побеждённого участника до окончания боя и во всех вкладках. В `waiting`
экипировка доступна; после завершения всех активных боёв блокировка снимается.
Остальные операции с предметами в рюкзаке сохраняют свои правила; зелье из
боевого снимка используется обычной командой боя.

REST возвращает `equip`/`unequip` как неактивные действия с причиной
«Нельзя менять экипировку во время активного боя». Прямая команда получает
HTTP 409 без изменения вещей, проекций и квитанции. Повтор уже успешно
сохранённого `operationId` возвращает прежний результат без повторной мутации.
Кнопки, двойной щелчок и контекстные действия используют серверные `actions`;
устаревшее окно после 409 перечитывает REST-состояние.

Дополнительный контейнер через совместимый API может иметь 1–200 мест.
Лимит — 20 контейнеров и 5000 экземпляров на владельца. Предметы вне контейнера
не занимают места контейнера, но учитываются в лимите экземпляров. Переполнение,
неположительное/дробное количество и недостаток предметов отклоняются целиком.

`InventoryService.receive(ownerId, itemId, quantity, operationId, inventoryId?)`
доступен серверным наградам и сценариям. Без `inventoryId` используется рюкзак,
`null` выдаёт предмет вне контейнера. Бесплатного HTTP-endpoint выдачи нет.
Все публичные мутации требуют UUID `operationId`.

## Конкуренция и повторы

Чистое ядро `applyInventoryCommand` возвращает новое состояние, не изменяя
загруженный снимок. Сервис сохраняет именно возвращённые `states` и на их
основе пересчитывает проекции персонажа. Успешный ответ означает, что новое
состояние предметов, бонусы и квитанция операции сохранены одной транзакцией.

Перед изменением модуль фиксирует запрос в `inventory_operations` внутри той же
транзакции. Повтор с тем же ID и параметрами возвращает прежний результат без
повторного действия, даже если исходный экземпляр уже удалён или передан.
Повтор ID с другими параметрами возвращает 409.

Владельцы блокируются через сервис персонажей в стабильном порядке UUID, затем
загружается имущество и повторно проверяется принадлежность экземпляров.
Изменения контейнеров/экземпляров, выдача навыка свитком, проекции персонажа и
результат операции коммитятся вместе. При замене экипировки адаптер хранения
должен сначала освободить прежний слот, затем записать новую вещь в той же
транзакции: уникальность слота владельца не зависит от порядка UUID. Любая ошибка откатывает всё. Неуспешная
операция не оставляет квитанцию об успехе и может быть повторена с тем же ID.

Клиент сохраняет ID неоконченной операции при сетевом/серверном отказе и повторяет
его при повторе того же действия. Если запись прошла, но обновление экрана не
удалось, повтор сначала восстанавливает экран, не выполняя действие второй раз.
После успешного обновления следующий осознанный клик получает новый ID.
Квитанции пока сохраняются бессрочно; удаление требует отдельной политики,
согласованной с допустимым сроком повторов.

## Совместимость и проекции

Единственная миграция `init` создаёт таблицы инвентаря сразу в актуальной
схеме v1 и выдаёт стартовые экземпляры десяти тестовым героям. Переход старых
JSON-инвентарей между вариантами разработки не поддерживается; для изменившейся
базовой схемы разработчик пересоздаёт локальные тома по README.

`Character.inventory` остаётся совместимой проекцией ненадетых стэков основного
рюкзака для старого UI и боевого снимка. Для надетого экземпляра `inventoryId`
сохраняет связь с основным рюкзаком владельца, но `equippedSlot` означает
отдельное место на персонаже. Эти предметы исключаются из занятости рюкзака
и проекции его стэков; смена схемы хранения не требуется.
`equipmentBonuses` — проекция экипировки.
После инициализации источник истины — таблицы модуля инвентаря. Только
`InventoryService` обновляет эти проекции через `CharactersService` в общей
транзакции. Нельзя начислять предметы изменением JSON `Character.inventory`.
Содержимое дополнительных контейнеров и предметы вне контейнеров не попадают
в бой. Изменение постоянного инвентаря после старта не меняет активный снимок.

## Интерфейс

Отдельный экран «Экипировка» (`/#equipment`) доступен из основной навигации
и карточки героя. Выбор любого слота показывает надетую вещь и подходящие
экземпляры из основного рюкзака. Кнопки «Надеть», «Заменить надетое» и
«Снять в рюкзак» используют существующие операции `InventoryService`;
доступность и причины запрета берутся из серверных `actions`. После действия
перечитываются имущество и персонаж, обновляются бонусы и занятость рюкзака.
Пустые слоты, дополнительные слоты каталога и запрет снятия при полном рюкзаке
поддерживаются так же, как на экране инвентаря. При смене героя выбор слота
сбрасывается; перезагрузка восстанавливает сохранённую экипировку через REST.

Экран доступен через вкладку «Инвентарь», кнопку в карточке героя и `/#inventory`.
За образец взята структура [инвентаря Perfect World](https://pwonline.ru/game.php?show=guide_interface):
надетые предметы вокруг силуэта персонажа и ячейки рюкзака в том же окне.
Это ориентир компоновки; баланс, каталог и слоты остаются правилами проекта.
На этом экране боковая панель должна содержать компактный выбор героя и
сворачиваемое создание персонажа. Характеристики и предметы не дублируются
в боковой панели; боевой индикатор энергии скрыт.

- Раздел «Экипировка» должен показывать надетые вещи отдельно от рюкзака,
  подписи пустых слотов и характеристики персонажа с бонусами снаряжения.
  Слоты из каталога, отсутствующие в стандартной раскладке, также отображаются.
- «Рюкзак» должен показывать сетку ячеек, количество в стэках и занятость без
  экипировки. Ёмкость берётся с сервера. Поиск, фильтр групп и сортировка меняют
  только представление; пользовательские позиции вещей пока не сохраняются.
- Нажатие на предмет в рюкзаке или слоте должно открывать его свойства и действия.
  Пустой слот фильтрует рюкзак по подходящему `equipSlot`. Надеть, заменить и снять
  можно кнопкой; двойной щелчок над вещью выполняет доступное надевание/снятие.
- Неактуальные действия отключаются по серверному ответу. Для снятия при полном
  рюкзаке показывается причина. Карточка должна показывать описание, бонусы,
  количество и состояние вещи; при замене — название возвращаемой вещи.
- Разделение/объединение стэков сохраняются. Передача другому персонажу и удаление
  доступны как вторичные действия в карточке. Передача идёт в основной рюкзак
  получателя. Удаление раскрывает явную кнопку с количеством и предупреждением
  о необратимости. Действия «Создать инвентарь» и «Убрать вне инвентаря» отсутствуют.
- Вещи в прежних дополнительных контейнерах и вне контейнера нельзя терять:
  при их наличии отображается сворачиваемый раздел «Другие сохранённые предметы».
  Карточка позволяет вернуть их в рюкзак с серверной проверкой вместимости.

Инвентарь загружается через REST; WS для этого экрана не используется.
После ошибки команды клиент перечитывает состояние и доступные действия.

Сохраняется открытая модель владения MVP: любой персонаж доступен любой вкладке.
Это не система авторизации; её добавление должно проверять доступ к обоим
владельцам и не менять транзакционные гарантии переноса.

## REST

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/v1/characters/:id/inventory` | Совместимый список стэков рюкзака с описаниями |
| GET | `/api/v1/characters/:id/inventories` | Все контейнеры, экземпляры, определения, группы и доступные действия |
| GET | `/api/v1/item-instances/:id` | Экземпляр, описание и действия |
| POST | `/api/v1/characters/:id/inventories` | `{operationId, name, capacity?}` |
| POST | `/api/v1/inventory-transfers` | `{operationId, instanceId, targetInventoryId, quantity}` |
| POST | `/api/v1/inventories/:id/items` | Положить: `{operationId, instanceId, quantity}` |
| DELETE | `/api/v1/item-instances/:id` | Удалить: `{operationId, quantity}` |
| POST | `/api/v1/item-instances/:id/actions` | `{operationId, action, ...параметры}` |

`action`: `remove`/`split` с `quantity`, `merge` с `targetInstanceId`, либо
`equip`, `unequip`, `read` без дополнительных полей. Ответ записи содержит
`itemIds`, `deletedItemIds` и, при создании контейнера, `inventoryId`.
`400` — нарушены ограничения; `404` — предмет/контейнер не найден; `409` —
конфликт повтора или изменение принадлежности во время конкурентного запроса.

## Качество созданных предметов

Крафт сохраняет `ItemInstance.quality` со снимком ранга и допами. Все переносы,
смена владельца и экипировка сохраняют эти данные; объединение требует равного
качества. Для legacy-качества множитель ранга усиливает базу; у качества v1 ранг
определяет число допов. Допы добавляются к
проекции модификаторов персонажа. Канонические свойства принадлежат inventory.
Инвентарь и экипировка показывают рамку цвета ранга, текст ранга и список допов.
Текст и серверные данные доступны через REST; цвет не единственный индикатор.

Реализовано: новый экземпляр сохраняет itemLevel и
версионированные снимки допов с конечной величиной и activationChanceBps,
по [общим правилам допов](modifiers.md) и [развитию предметов](item-progression.md).
Ранг определяет количество допов, itemLevel — их величину; текущий множитель
базы от ранга сохраняется только у старой версии. Перенос и надевание не
перебрасывают ни состав, ни величины. Постоянный статовый бонус имеет 100%
применение; случайное срабатывание требует поддержанного боевого trigger.
Индивидуальный craftWeight влияет на создание, не на пересчёт экипировки.


`ItemInstance.effects` хранит снимок состава расходника в `item_instances.effects`.
При создании он копируется из определения, а дальнейшие переносы, разделение
и сохранение не перечитывают его из каталога. Объединение требует одинаковых
составов. `Character.inventory` и боевой рюкзак сохраняют этот массив вместе
с ID и количеством; канонический экземпляр остаётся в inventory.


## Постоянный расход зелий в бою

`InventoryService.state` должен загружать канонический инвентарь под блокировкой
владельца при старте. Бой должен фиксировать экипировку, рюкзак и не более 10
зелий в поясе. Успешное применение вызывает `consumeBattleItem` в транзакции
боевой команды: сервис должен проверить владельца, основной рюкзак, ID и состав
бутылки, уменьшить количество, удалить пустой стэк и обновить проекцию персонажа.
Повтор старой команды не должен списывать вторую бутылку. Перемещение, удаление,
разделение и объединение зелий активного участника должны быть заблокированы
как в серверных действиях интерфейса, так и при прямой команде. Крафт и выдача
не пополняют пояс текущего боя. Подробные правила — [items.md](items.md#боевой-пояс).
