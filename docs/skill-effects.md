# Навыки: цели, эффекты и длительность

Статус: реализована первая очередь — цели участников, модификаторы
характеристик, очищение, составные урон/лечение, сроки и повторное наложение.
Поле, периодический урон/лечение и щиты остаются следующим этапом. Правила
характеристик — в [character.md](character.md), энергия — в [combat.md](combat.md).

## Реализованная первая очередь

Новые снимки содержат `effectsVersion: 1`; старые активные бои без этого поля
продолжаются по прежним правилам. При старте ожидающей комнаты берётся свежий
контент. `CombatVersion` остаётся 2: последовательность хода и общая энергия
не меняются.

`Skill.targeting` задаёт `self`, `ally_single`, `enemy_single`, `allies_all`
либо `enemies_all`. У одиночного союзника `includeSelf` по умолчанию false,
у группы союзников — true. Основной выбор делает игрок; `recipient: caster`
позволяет отдельному эффекту воздействовать на применяющего один раз.

`Skill.effects[]` поддерживает четыре обработчика:

| kind | Поведение |
| --- | --- |
| `stat_modifier` | Временное изменение любого ID реестра; четыре операции модификаторов |
| `dispel` | Снятие до `maxCount` снимаемых бафов или дебафов; опциональный фильтр тегов |
| `damage` | Формула HP от характеристик, тип урона и признак возможности крита |
| `heal` | Формула HP от характеристик; ограничение текущим максимумом |

`power`, `effect` и `powerPerLevel` остаются совместимостью старых навыков.
Если задан `effects[]`, он определяет исполнение, а уровень меняет веса
`weightBps + (rank - 1) × weightPerRankBps` его выражений. Выражения используют
характеристики `caster`/`target`, целые базисные пункты, границы и единицу.
Для урона/лечения нужна хотя бы одна ссылка на характеристику и единица HP.
Проценты — в базисных пунктах. Длительность — `durationTurns` 1–20 либо
выражение с единицей `turns`, ограниченное этим диапазоном.

При применении фиксируются величины и длительности всех эффектов из одного
состояния до первого эффекта. Затем эффекты выполняются в порядке массива:
дебаф защиты перед уроном уже влияет на защиту, а собственный баф перед ударом
не увеличивает рассчитанную силу этого же каста. После смерти получателя
дальнейшие эффекты по нему пропускаются; эффект на применяющем выполняется
один раз. Формула защиты остаётся действующим вычитанием, описанным в
[character.md](character.md); предлагаемый ниже переход к относительной
защите в эту реализацию не входит.

`Fighter.activeEffects[]` содержит экземпляры с `instanceId`, `definitionId`,
именем, источником/уровнем навыка, `magnitude`, единицей, `statId`/операцией,
полярностью, тегами и признаком снятия. Срок: `remainingTurns`, `eligibleFromTurn`
и локальный `Fighter.turnsStarted`. Также сохраняются `appliedSequence`,
`stackKey`, `stacking`, `stacks`, `maxStacks`, `priority`.

Эффект действует сразу. Ход, уже идущий при наложении, не учитывается.
В конце каждого следующего собственного хода получателя срок уменьшается;
при нуле источник удаляется и характеристики пересчитываются из оставшихся.
Баф на два хода, применённый на себя, переживает текущий ход и следующие два
собственных хода, затем снимается. Смена источника/времени ожидания не меняет
срок. Перезагрузка и REST GET не расходуют ходы.

Повторное наложение по общей группе `stackKey`:

- `refresh`: заменить снимок величины и обновить полный срок; по умолчанию.
- `replace_if_stronger`: слабый не меняет величину/срок, равный обновляет срок,
  сильный заменяет. Применимо к `add_flat`/`add_percent`.
- `stack`: складывать аддитивные модификаторы до `maxStacks`; величина единицы
  заменяется свежим снимком, общий срок обновляется.
- `independent`: независимые экземпляры со своими сроками; на пределе заменить
  самый ранний. По умолчанию для стеков/независимых экземпляров предел 3.

На бойце допускается до 64 активных эффектов, действует общий лимит 512
модификаторов расчёта. Несовместимые группы, неизвестные ссылки, неверные
единицы и операции отвергаются при загрузке контента. Неверная цель или
ошибка применения не расходуют энергию и не меняют бой.

Очищение снимает подходящие `dispellable`-эффекты по порядку применения, затем
ID. Бафы и неснимаемые дебафы при очищении дебафов сохраняются. При отсутствии
подходящих эффектов действие всё равно расходует энергию и перезарядку.
При смерти удаляются собственные эффекты погибшего, но его эффекты на других
продолжают действовать. Увеличение maxHp не лечит; уменьшение ограничивает HP.

Обработчики — чистые `core/effects`, формулы — `core/formulas`, разрешение
целей — `core/targeting`. Применение, расходы, перезарядки, RNG и ход сохраняются
в одной транзакции агрегата боя. `temporaryModifiers` — проекция активных
эффектов; постоянные персонажи и вещи не изменяются. NPC используют тот же
механизм и выбирают полезные усиления/ослабления/очищение, не обновляя без
необходимости уже действующий эффект. Прежние NPC-каталоги получают адаптер
характеристик только в снимке боя.

REST и WS передают действующие эффекты, сроки и серверные `targetIds`,
`targeting`, `effectPreviews` в `skillChoices`. UI выбирает только допустимые
цели, показывает рассчитанную величину и срок. Значки под бойцом раскрывают
источник, изменение параметра, стэки, оставшиеся собственные ходы и возможность
снятия. Эффекты входят и в `playback`; восстановление не зависит от WS.

В MongoDB seed добавляет семь навыков из `core/effects/content.ts` через
`$setOnInsert`, сохраняя пользовательские изменения. Бесплатного изучения нет:
навыки доступны во вкладке «Навыки» за обычные очки. Все имеют 10 уровней.

| ID | Навык | Действие при интеллекте 10, ранг 1 |
| --- | --- | --- |
| `battle-cry` | Боевой клич | +20% силы себе/союзнику, 2 хода |
| `weakening` | Ослабление | -20% физической мощи противника, 2 хода |
| `fire-vulnerability` | Уязвимость к огню | -25% защиты от огня, 2 хода |
| `purify` | Очищение | Снять один снимаемый дебаф себе/союзнику |
| `stone-skin` | Каменная кожа | +50% своей физической защиты, 2 хода |
| `arcane-focus` | Магическая концентрация | +20% магической мощи себе/союзнику, 2 хода |
| `rending-strike` | Рассекающий удар | -25% физической защиты на 2 хода, затем физический урон |

Далее сохранён проект полного расширения: периодические эффекты, щиты,
заморозка поля, более общий контракт часов и будущая формула сопротивления.
При расхождении с проектом выше описано текущее реализованное поведение.

## Требования и проектные решения

Подтверждённые требования пользователя:

- Навык имеет цель: себя, одного союзника, союзников, одного противника,
  всех противников либо поле.
- Для одиночной цели игрок должен выбирать участника; для поля — клетку.
- Навык должен описывать эффекты, бафы, дебафы и их продолжительность.
- Величины воздействия рассчитываются от характеристик; базовые
  характеристики и их расширение описаны в документе персонажа.

Сохраняются предыдущие требования: только изученные навыки типов прямого
совпадения видны после всех каскадов; нехватка энергии и перезарядка блокируют
кнопку; применение расходует энергию и завершает ход. Скрывать подходящий навык
из-за отсутствия цели нельзя — он должен оставаться видимым с причиной.
Четыре очка на старте, единственный начальный физический навык и 10 уровней
сохраняются. Защита остаётся типом клетки и энергии, без отдельной ветки навыков.

Далее зафиксирован рекомендуемый проект: союзник по умолчанию исключает себя,
группа союзников включает себя; время измеряется ходами владельца эффекта;
заморозка запрещает ручную перестановку клетки. Числа примеров, рост
коэффициентов, критические эффекты и политика повторного наложения — предложения
для первого выпуска. Они явно отделены от работающих правил v2.

## Определение навыка и боевой экземпляр

`SkillDefinition` из каталога описывает `id`, название, описание, `element`,
цену энергии `cost`, перезарядку `cooldown`, требования `learning`, рост
`progression`, `targeting` и упорядоченный массив `effects`. `element` определяет
энергию и открытие навыка совпадением; он не определяет отношение к цели.
Навык воды может атаковать, лечить, снимать дебаф или изменять поле.

`effect` и единственная плоская `power` уступают место `effects[]` и формулам
величин. Уровень навыка меняет коэффициенты этих формул, а не добавляет
готовое число урона. Длительность и шанс могут иметь отдельные выражения.
Цена и перезарядка по умолчанию остаются числами каталога; их изменение от
уровня или характеристик потребует явной политики, не должно появляться скрыто.

`LearnedSkill` — ID и уровень 1–10 на персонаже. `EffectDefinition` — описание
поведения в каталоге. `ActiveEffect` — конкретный временный эффект в бою:

| Поле | Назначение |
| --- | --- |
| `instanceId`, `definitionId` | Уникальность экземпляра и ссылка на определение из снимка |
| `sourceFighterId`, `sourceSkillId`, `sourceRank` | Источник и уровень при применении |
| `target` | ID участника либо координата клетки |
| `polarity`, `tags`, `dispellable` | Баф/дебаф/нейтральный, классификация и возможность снять |
| `resolvedMagnitude` | Вычисленная при наложении величина, её единица и нужный вид урона |
| `clock`, `clockFighterId`, `remainingTurns` | Чей счётчик времени используется и сколько ходов осталось |
| `appliedSequence`, `eligibleFromTurn` | Порядок применения и первый учитываемый ход |
| `stackKey`, `stacks`, `maxStacks`, `stacking` | Группа и политика повторного наложения |
| `state` | Остаток щита либо другое состояние конкретного обработчика |

Мгновенный урон и лечение не создают активный экземпляр. Боевые эффекты не
изменяют постоянного персонажа или предмет. Снимок должен содержать исходные
определения и рассчитанные значения, чтобы переживать перезапуск без перечитывания
нового каталога. Обновление контента влияет только на следующие бои.

## Цели

| `targeting.kind` | Кого затрагивает | Что выбирает игрок |
| --- | --- | --- |
| `self` | Только живого применяющего | Ничего, подтверждает применение |
| `ally_single` | Одного живого союзника | Карточку союзника |
| `allies_all` | Всех живых союзников | Ничего; видит подсветку всей группы |
| `enemy_single` | Одного живого противника | Карточку противника |
| `enemies_all` | Всех живых противников | Ничего; видит подсветку всей группы |
| `battlefield_cell` | Одну клетку общего поля | Координату `{row, col}` |

У `ally_single` параметр `includeSelf` по умолчанию `false`, у `allies_all` —
`true`. Чтобы один и тот же лечебный навык позволял лечить и себя, и союзника,
каталог должен явно задать `ally_single, includeSelf: true`. Самолечение через
`self` не превращается в возможность выбрать другого участника.

У мёртвых участников нет допустимых действий и они не входят в обычные цели;
воскрешение не входит в первый выпуск. Если в одиночном бою `ally_single`
исключает себя, такой навык виден, но заблокирован: `NO_VALID_TARGET`.
У массового навыка цена энергии и перезарядка применяются один раз за
применение, а полная величина эффекта — каждому выбранному сервером участнику.
Деления общей силы на число целей нет; баланс задаётся коэффициентом навыка.

Список живых целей фиксируется после проверки команды, до исполнения эффектов.
Порядок — стабильный по ID. Если цель погибла от первого эффекта, последующие
обычные эффекты по ней пропускаются, а не выбирают нового участника. Смерть
не отменяет уже выполненное применение и не возвращает его цену.

`targeting` описывает основной выбор. Каждый эффект имеет `recipient: selected`
либо `caster`: так атака может ударить выбранного противника и дать баф себе.
Произвольный второй выбор цели, цепочки, конусы, области вокруг клетки и
неявное перенаправление к другому противнику в первую версию не входят.
Эффект клетки допускает только `selected` у `battlefield_cell`; воздействие на
участника — выбранных участников или `caster`. Несовместимая комбинация
отклоняется при валидации контента. Один каст может сочетать эффект поля и баф
источника, но не требует дополнительной одиночной цели.
`recipient: caster` выполняется один раз за эффект, независимо от числа
участников, выбранных массовой целью.

## Эффекты и обработчики

| `kind` | Смысл и основные параметры |
| --- | --- |
| `damage` | Мгновенный урон: выражение величины, вид урона, `canCrit` |
| `heal` | Мгновенное лечение: выражение величины, ограничение максимумом HP |
| `stat_modifier` | Баф/дебаф: `statId`, операция из документа персонажа, величина, длительность |
| `periodic_damage` | Урон в начале учитываемого хода цели: величина, вид, длительность |
| `periodic_heal` | Лечение в начале учитываемого хода цели: величина и длительность |
| `shield` | Поглощение урона: рассчитанная ёмкость, остаток, длительность |
| `dispel` | Снять эффекты по `polarity`/тегам, с лимитом количества |
| `cell_freeze` | Заморозить выбранную клетку: длительность, правила повторного наложения |

Баф — положительный временный эффект, дебаф — отрицательный; это не отдельные
реализации изменения чисел. Они задаются `polarity: buff | debuff | neutral`
и типом обработчика. Например, ослабление атаки — `stat_modifier` с отрицательным
`add_percent`, а горение — `periodic_damage` с тегом `burning`. Положительный
процент с ошибочной полярностью не должен молча менять смысл: валидатор
проверяет простые известные случаи, составные случаи отражает описание каталога.

Массив эффектов выполняется в порядке каталога. Модуль характеристик пересчитывает
получателя после каждого изменения его модификаторов. Формулы источника и
получателя для **всех** эффектов одного каста вычисляются из одного состояния
до его первого эффекта. Поэтому баф первым эффектом не увеличивает исходную
силу второго эффекта того же каста. Сопротивление и остаток щита при получении
урона, в том числе внутри того же каста, берутся текущие: дебаф брони перед
ударом действительно ослабляет защиту. Новый баф источника меняет силу
следующих кастов. Это правило устраняет циклический расчёт исходной величины.

Каждый обработчик регистрируется по `kind` и содержит схему параметров,
проверку совместимости цели, применение/тик/удаление и представление результата.
Новый навык из уже известных эффектов добавляется данными. Новый вид эффекта
требует одного обработчика и его тестов; нельзя добавлять `switch (skill.id)`
в боевой движок или отдельные классы на каждое название навыка.

Для первой версии не вводятся оглушение, отражение, вампиризм, воскрешение и
срабатывания «при каждом ударе». Их будущие обработчики должны иметь отдельные
правила последовательности и ограничение рекурсии, а не скрытый вызов каста.

## Выражения величин и рост навыка

Фрагмент определения стартового удара (поля обучения и описания опущены):

```json
{
  "id": "strike",
  "element": "physical",
  "cost": 3,
  "cooldown": 0,
  "progression": { "maxLevel": 10, "pointCost": 1 },
  "targeting": { "kind": "enemy_single" },
  "effects": [{
    "id": "strike-hit",
    "kind": "damage",
    "recipient": "selected",
    "damageType": "physical",
    "canCrit": true,
    "magnitude": {
      "unit": "hp",
      "terms": [{
        "scope": "caster",
        "statId": "physicalPower",
        "weightBps": 15000,
        "weightPerRankBps": 1000
      }],
      "rounding": "floor",
      "min": 0,
      "max": 1000000
    }
  }]
}
```

`EffectDefinition.id` уникален внутри навыка; глобальная ссылка на определение
составляется из ID навыка и эффекта в зафиксированном снимке. Новый формат
`progression` больше не содержит `powerPerLevel`: рост хранится в выражениях.

Выражение содержит сумму взвешенных ссылок на зарегистрированные характеристики
`caster` или `target`, способ округления `floor`, границы и единицу результата.
Вес хранится в целых базисных пунктах. Коэффициент на уровне `r`:

```text
weight(r) = weightBps + (r − 1) × weightPerRankBps
value = clamp(floor(sum(referenceValue × weight(r)) / 10000), min, max)
```

`target` в выражении — получатель конкретного эффекта; у `recipient: caster`
им является источник. Для групп величина рассчитывается по каждому получателю
из одного состояния до каста. Выражение длительности оверлея клетки не может
ссылаться на `target`-участника: у клетки нет характеристик.

Например, первая сила навыка берётся из `physicalPower`, вес 15000, прибавка
к весу за уровень 1000. При мощности 8 навык уровня 1 даёт 12 сырого урона,
уровня 10 — 19. Базовые характеристики, экипировка, бафы и дебафы влияют на
мощность; ранг меняет эффективность её использования. Прямые сокращения
и каскады не входят в формулу навыка.

Для `add_percent` результат выражения измеряется в базисных пунктах. Например,
`caster.intelligence × 200` при интеллекте 10 даёт 2000 = +20%; соответствующий
вес равен 2 000 000; общий лимит веса выражений и формул реестра — 10 000 000.
Для постоянного бонуса предмета или простого бафа допускается константа
`{constant: 2000, unit: basis_points}`. Для урона, лечения и щита константа
не может быть единственным источником силы: нужна хотя бы одна ссылка на
характеристику. Ссылка `target.maxHp` позволяет описать лечение на 20% максимума,
не создавая специальное поле для каждого процента.

Длительность фиксируется при наложении. Она может быть числом каталога 1–20
либо выражением с единицей `turns`, теми же ссылками и итоговым ограничением
1–20. Пример: `floor(caster.intelligence × 0.2)`, ограничить 1–5 ходами;
при интеллекте 10 получается 2. Последующий баф интеллекта не продлевает уже
наложенный эффект. Начальное предложение для обычных бафов — 2 хода.

В первой версии величина периодического эффекта, прибавка и ёмкость щита
фиксируются при наложении (`snapshot`). Защита от каждого тика берётся текущая.
Автоматического пересчёта источника при каждом тике нет; смерть источника
не удаляет его эффекты с других живых участников.

## Урон, лечение, щиты и удача

Рекомендуемая формула урона нового выпуска:

```text
raw = выражение эффекта от характеристик до этого каста
criticalRaw = raw × (10000 + criticalBonusBps) / 10000, если выпал крит
              иначе raw
resistance = armor для physical, magicResistance для четырёх стихий
resistance += временная защита прямых клеток (число × guardPerCell)
damageBeforeShield = max(1, floor(criticalRaw × K / (K + resistance)))
hpDamage = max(0, damageBeforeShield − поглощённое щитами)
```

Если `raw = 0`, итог равен 0 без проверки крита. Нижняя граница сопротивления
0; `K > 0`, предлагается 30 в `balance.formulas.damageMitigationK`. Такая
формула позволяет защите снижать долю урона без отрицательных значений. При
мощности 8 и весе 15000 получается 12 сырого урона; броня 3 оставляет 10,
а броня 3 и временная защита 30 оставляют 5. Формула v2 через вычитание
продолжает работать только в сохранённых боях v2.

Каждый мгновенный `damage` с `canCrit: true` проверяет шанс удачи один раз
на получателя. Для первого выпуска включать крит у обычных атак, отключать
у периодического урона и лечения. Эффекты контроля применяются гарантированно,
если допустимы; удача не даёт скрытую вероятность неудачного бафа или заморозки.

RNG принадлежит серверу и внедряется в чистый движок. Состояние генератора
сохраняется в агрегате боя; порядок целей и эффектов задаёт порядок выборок.
Транзакционный откат не расходует сохранённое состояние RNG. Повтор с устаревшей
версией не может «перебросить» крит. Алгоритм генератора фиксируется версией
движка и не использует присланный клиентом результат. Журнал результата
содержит признак крита, реальный урон HP и поглощение щитом.
Состояние RNG — внутреннее поле сохранённого агрегата; оно не входит в
публичные REST/WS-снимки и не может обновляться клиентской командой.

Щиты поглощают урон после защиты, начиная с ближайшего истечения, затем по
порядку применения и ID. Исчерпанный щит удаляется. Лечение не восстанавливает
его остаток. Лечение: `min(вычисленная величина, maxHp − hp)` у живой цели.
Полностью здоровая живая цель допустима: чистое лечение восстанавливает 0,
но применение тратит энергию. Это позволяет составным навыкам лечить и давать
баф без отдельного неявного правила. UI должен предупреждать о нулевом лечении.

После каждого эффекта смерти фиксируются, а победа проверяется после всей
партии эффектов/тиков. Массовый навык не должен закончить бой посередине списка
целей. Если живых команд не осталось, фиксируется ничья. Погибший теряет свои
эффекты; наложенные им эффекты на других продолжают действовать.

## Срок действия и повторное наложение

Длительность измеряется собственными ходами получателя, а не общим `Battle.turn`.
Для эффектов поля используется счётчик применившего (`source_turns`), поскольку
поле общее. Мгновенный эффект длительности не имеет.

Новый эффект не расходует длительность на ход, уже идущий в момент наложения.
Первый учитываемый — следующий начавшийся ход его `clockFighterId`. В начале
каждого учитываемого хода срабатывают периодические эффекты, в конце этого
хода уменьшается `remainingTurns`; при 0 эффект удаляется. Баф на 2 хода,
наложенный на себя в своей фазе выбора, действует в следующих двух собственных
ходах и между ними, затем исчезает. Дебаф на противника на 2 хода тикает в
началах его следующих двух ходов и заканчивается после второго.

Порядок начала хода: выбрать живого участника → снять его защиту прямых клеток,
действующую до собственного хода → начать его локальный счётчик → выполнить
периодические эффекты в порядке `appliedSequence`, ID → пересчитать
характеристики → проверить смерти/волну/победу → при живом участнике открыть
`before` и обновить перезарядки по прежней семантике. Новые периодические
эффекты не могут порождать ещё один тик в той же партии.

Если тики убили участника до действия, его начавшийся ход всё равно считается
завершённым для часов эффектов, которыми он владеет; затем выбирается следующий
живой. Его собственные эффекты удалены вместе со смертью. Заморозка поля,
чьи часы привязаны к погибшему источнику, немедленно снимается, чтобы не
оставить вечное ограничение. Перезапуск сервера, время ожидания игрока и REST
чтения не уменьшают длительность; фоновые таймеры и очереди не нужны.

`stackKey` задаёт одну группу эффектов на получателе независимо от источника:
например, `burning` или `battle-cry`. Без группового ключа используется
`definitionId`. Варианты повторного наложения:

| `stacking` | Правило |
| --- | --- |
| `refresh` — по умолчанию | Один экземпляр; заменить величину свежим снимком, установить полную новую длительность, не делать дополнительный тик |
| `replace_if_stronger` | Заменить только при большей абсолютной величине; при равной обновить срок; более слабое не меняет эффект |
| `stack` | Увеличить число стэков до `maxStacks` (предложение: 3), заменить величину единицы свежей, обновить общий срок |
| `independent` | Независимые экземпляры до `maxStacks`; на пределе заменить самый старый |

Определения с общим `stackKey` должны иметь совместимые вид эффекта, операцию,
единицу, получателя и часы; несовместимая группа отвергается валидатором.

`replace_if_stronger` допускается только для сравнимой скалярной величины и
одинаковой операции/единицы. `stack` применим к периодическим эффектам и
аддитивным модификаторам: итог = величина единицы × стэки. Для `set`, `multiply`
и щитов `stack` запрещён; щит использует `refresh` или `independent`.
Обновление срока не выдаёт тик сразу. У обновлённого в уже идущий ход эффекта
первый учитываемый ход снова следующий. Снятие дебафа выбирает только
`dispellable: true`, по порядку наложения, затем ID; цена не возвращается,
если подходящего эффекта для снятия нет.

## Цель «поле»: заморозка клетки

На общем поле клетка — координата, а фишка — её текущее содержимое.
Рекомендуемый первый эффект `cell_freeze` закрепляется за **координатой**.
Он запрещает всем участникам ручную перестановку, у которой эта клетка
является началом или концом. Совпадения, удаление, падение и генерация в этой
координате работают обычно; заморозка остаётся на месте до окончания срока.
Она не означает заморозку персонажа и не уменьшает его ход.

Это решение сохраняет текущее понятие линии и не требует барьеров падения.
Полная блокировка сокращения или замораживание конкретной перемещающейся фишки —
другие эффекты с отдельной будущей спецификацией.

Заморозка накладывается после каскадов, когда уже выбран навык. Сама она не
делает совпадений, не начисляет энергию и не меняет `direct`/`generated`.
Срок по умолчанию — до завершения двух следующих собственных ходов источника.
Повторное наложение на клетку обновляет срок и владельца часов согласно `refresh`.
Поэтому оно допустимо и не должно искусственно скрывать навык.

Новые оверлеи должны храниться отдельно от матрицы типов: `Battle.cellEffects`.
Поле принимает нейтральные ограничения перестановки, например список
`blockedSwapCells`, а не ID навыков, участников, энергию или бафы.
Проверка хода, поиск хода NPC и проверка наличия ходов используют один и тот же
набор ограничений. Нельзя проверять их только в React.

Чтобы заморозка не создавала тупик, после изменения ограничений движок должен
убедиться, что разрешённый ход существует. Политика восстановления: снять
самые старые заморозки по `appliedSequence`, ID до появления хода; при этом
не генерировать новую доску, не выдавать энергию и записать снятие в результат.
После обычного каскада, если разрешённых ходов нет, сначала снять такие
ограничения; если ходов всё ещё нет без ограничений, использовать стандартную
перегенерацию с прежним размером и палитрой. При перегенерации все оверлеи
клеток снимаются, их исчезновение явно возвращается клиенту.
Навык, чью заморозку пришлось снять сразу, всё равно считается применённым;
UI показывает это в результате. Это рекомендуемая политика против тупика,
которую нужно подтвердить перед реализацией эффекта поля.

## Выбор в интерфейсе

До разрешения всех каскадов выбор навыка и цели недоступен. После получения
снимка `choose` клиент показывает серверные варианты и объяснение эффекта:
цель, текущие рассчитанные величины, длительность, цену и перезарядку.
Видны только изученные навыки прямых типов; нельзя показывать другие типы
ради наличия подходящей цели или бафа.

Нажатие доступного навыка выбирает его локально, без списания и HTTP-мутации.
Для одиночного участника подсвечиваются только допустимые карточки; для поля —
клетки. Первая выбранная клетка в этом режиме — цель навыка, а не начало
перестановки. Для себя/группы показывается автоматическая подсветка. Кнопка
«Применить» отправляет команду после выбора; «Отмена» и Escape снимают
локальный выбор бесплатно. Можно сменить навык или завершить ход без применения.

Смена версии боя, окончание своего хода, смерть выбранного участника и уход
со страницы сбрасывают локальный выбор. Во время отправки повторная отправка
из UI блокируется. При 409 клиент перечитывает бой и предлагает выбрать заново,
не повторяя каст автоматически. Бейджи эффектов показывают источник,
величину/стэки и оставшиеся собственные ходы; HP, щит и временная защита
показываются отдельно. Для заморозки необходимы значок, состояние недоступной
клетки и пояснение, что автоматические сокращения продолжают работать.

## Контракт REST для следующей версии боя

Транспорт остаётся REST: `POST /api/battles/:id/actions`. Конверт сохраняет
`characterId` и ожидаемую `version`. Новый вариант действия:

```json
{
  "characterId": "00000000-0000-4000-8000-000000000001",
  "version": 42,
  "action": {
    "type": "skill",
    "skillId": "ice-prison",
    "target": { "kind": "cell", "row": 2, "col": 4 }
  }
}
```

`target` — строгое объединение: `{kind: fighter, fighterId}` для одиночной
цели, `{kind: cell, row, col}` для поля, `{kind: automatic}` для себя и групп.
Передавать одновременно `targetId` и `target` запрещено. Лишние поля, координаты
вне фактического размера, неверный тип цели и присланные клиентом значения
урона/стэков отвергаются. У `automatic` сервер сам строит список; прислать список
участников вместо него нельзя.

Сервер возвращает полный снимок с `engineVersion` следующего выпуска,
`matchedElements`, `skillChoices`, эффективными характеристиками, эффектами,
щитами, оверлеями поля и структурированным `actionResults` последней команды.
Каждый результат содержит источник, навык, эффект, цель, фактическое изменение,
`critical` для урона, поглощение щитом, добавленные/снятые эффекты. Результаты
автоматических ходов NPC сохраняются отдельно в том же порядке. Это не новый
публичный поток событий: REST и WS передают один и тот же снимок после коммита.

Новая `SkillChoice` содержит `skillId`, `enabled`, массив стабильных
`blockers: {code, message}[]`, `targeting` и серверные `validFighterIds` либо
допустимую область клеток. Для маленького поля можно вернуть список клеток,
для полного поля — `{all: true}`; максимум поля остаётся 32 × 32.
Отсутствие выбранной одиночной цели — локальное состояние UI, а не причина
блокировать сам навык, если допустимые цели существуют. Точные величины для
конкретной цели считаются сервером при команде; UI может показывать величину
до защиты и текущие характеристики цели, не обещая точный критический исход.

Успешная команда выполняется атомарно под блокировкой боя:

1. Проверить ожидаемую версию, активного участника, фазу, тип прямого совпадения,
   изученность, энергию и перезарядку; разрешить выбранную цель и эффекты.
2. На рабочей копии зафиксировать цели и входные характеристики; вычислить
   выражения, списать энергию один раз, установить перезарядку и выполнить
   эффекты. Ошибка определения или расчёта отменяет весь каст.
3. Пересчитать характеристики, обработать смерти, волны и эффекты конца/начала
   ходов; NPC применяет тот же механизм выбора целей и эффектов.
4. Сохранить бой, состояние RNG, награды и outbox одной транзакцией;
   после коммита отправить снимок через WS и вернуть REST-ответ.

При откате никакой частичный урон, расход энергии, тик или крит не сохраняется.
Повтор команды с той же старой версией получает 409. Если ответ потерян,
клиент делает GET, проверяет новую версию/результаты и не отправляет каст
повторно с обновлённой версией без нового выбора игрока. Текущий проект не
имеет авторизации; `characterId` не является доказательством владения.
Этот дизайн не вводит отдельную систему доступа, но проверка участника боя,
активного хода и всех правил остаётся обязательной на сервере.

| Код | HTTP | Условие / действие клиента |
| --- | --- | --- |
| `BATTLE_VERSION_CONFLICT` | 409 | Состояние изменилось; перечитать и сбросить выбор |
| `BATTLE_NOT_FOUND` | 404 | Бой отсутствует; прекратить отправку |
| `NOT_ACTOR_TURN`, `INVALID_PHASE` | 400 | Чужой ход либо навык до совпадений |
| `SKILL_NOT_LEARNED`, `ELEMENT_NOT_MATCHED` | 400 | Навык неизвестен либо его тип не совпал напрямую |
| `INSUFFICIENT_ENERGY`, `SKILL_ON_COOLDOWN` | 400 | Сохранить видимость, показать причину |
| `TARGET_REQUIRED`, `TARGET_KIND_MISMATCH` | 400 | Выбрать цель правильного типа |
| `INVALID_TARGET`, `NO_VALID_TARGET` | 400 | Мёртвая/чужая цель или нет допустимых целей |
| `INVALID_CELL`, `CELL_SWAP_BLOCKED` | 400 | Координата вне поля или попытка перестановки замороженной клетки |
| `INVALID_SKILL_DEFINITION` | 500 | Невалидный сохранённый контент/ошибка вычисления; откат и диагностический журнал |

Стабильные коды — новый контракт; действующий сервер пока возвращает текстовые
ошибки. Не нужно публиковать отдельный endpoint для каждого эффекта или
вызывать WS-команду применения. Отказ Redis/очереди не меняет исход каста;
недоступность PostgreSQL не позволяет подтвердить действие. Повторы архива
используют существующий outbox, вычислять тики через BullMQ запрещено.

## Разделение ответственности и данные

- `skills`: каталог определений, требования, выучить/улучшить/выдать. Навык
  не хранит отдельное глобальное «оставшееся время» и не меняет бой репозиторием.
- `characters`: реестр характеристик и постоянная база; `inventory` отдаёт
  постоянные модификаторы экипировки через свою проекцию.
- Чистые `core/attributes`, `core/formulas`, `core/targeting`, `core/effects`:
  граф и пересчёт, выражения, выбор допустимых целей, обработчики и сроки.
  `core/combat` оркестрирует их; отдельные эффекты не вызывают HTTP/БД.
- `battles`: единственный владелец `ActiveEffect`, ресурсов, локальных часов,
  RNG и клеточных оверлеев; сохраняет их в существующем JSONB боя.
- `battlefield`: геометрия, сокращения, падение, генерация, допустимые
  перестановки с ограничениями. Он не знает каталог навыков и характеристики.
- `web/features/battles`: режим выбора навыка и участника, подтверждение,
  отображение эффектов; `features/battlefield` получает режим выбора клетки
  и оверлеи через props. Клиент не применяет эффекты самостоятельно.

Не создавать репозиторий бафов, очередь тиков или отдельный микросервис эффектов:
состояние меняется в одной транзакции боя. Извлекать сервис стоит только при
появлении независимого жизненного цикла эффектов вне боя и своей нагрузки;
до этого чистые модули уже дают заменяемость обработчиков.

Предлагаемые лимиты в политике контента: до 16 эффектов на навык, 64 активных
экземпляра на участника, один `cell_freeze` на клетку; длительность 1–20,
до 10 независимых стэков. Новый эффект при заполненном лимите снимает самый
старый экземпляр, затем добавляется; результат снятия виден клиенту.
До 32 ссылок в выражении, абсолютное значение веса до 10 000 000, результата
до 1 000 000; переполнение отклоняется, а не обрезается неявно.
Временные эффекты удаляются при смерти получателя и в конце боя; в архиве
сохраняется финальный снимок и журнал результатов. Вне боя эффектов первой
версии нет. Запись журнала должна включать ID боя, версию, актёра, навык,
цели и код ошибки; метрики ошибок не должны использовать ID как labels.

## Примеры каталога

Числа — предложения для баланса; ID существующего навыка нельзя менять
ради переименования цели или эффекта без миграции зависимостей и свитков.

| Пример | Цель | Эффекты от характеристик |
| --- | --- | --- |
| Удар, physical | `enemy_single` | `damage: 150% physicalPower`, +10 процентных пунктов коэффициента за ранг, крит разрешён; цена 3, КД 0 |
| Источник, water | `ally_single`, включая себя | `heal: 150% healingPower` |
| Боевой клич, physical | `self` | `physicalPower + intelligence × 200` базисных пунктов на 2 хода |
| Благословение, air | `allies_all`, включая себя | Каждому `armor + 40% caster.dexterity` на 2 хода |
| Инферно, fire | `enemies_all` | Каждому урон от `magicPower`, затем горение от снимка `magicPower` на 2 хода |
| Ослабление, earth | `enemy_single` | `physicalPower − 2000` базисных пунктов на 2 хода |
| Ледяная печать, water | `battlefield_cell` | `cell_freeze` на `floor(intelligence × 0.2)` ходов, ограничить 1–5 |

Для примера «Благословение» плоская прибавка брони при ловкости 10 равна 4;
это 40% характеристики источника, а не +40% брони получателя. «Ослабление»
уменьшает рассчитанную мощь цели на 20%, не её базовую силу навсегда.
Усиление физической мощи можно масштабировать силой вместо интеллекта —
конкретная связь задаётся данными навыка, а не названием группы.

## Поставка, совместимость и открытые решения

Реализация требует новой версии движка (предлагается `engineVersion: 3`)
с прежней экономикой совпадений. Это отделяет новые формулы, цели и эффекты
от уже сохранённых `combatVersion: 2` и ещё более старых боёв.

1. Добавить реестр, чистый расчёт и новые схемы контента; сохранить чтение старых
   форматов, не переписывать старые миграции и боевые снимки.
2. Подготовить идемпотентную миграцию базы/бонусов и каталогов. Обучение хранит
   те же ID/ранги; новые требования ссылаются на реестр. Старые требования
   `attack`, `defense`, `maxHp` переводятся на соответствующие производные
   параметры чистой базы; `maxEnergy` остаётся проверкой правила 30.
3. Преобразовать все существующие `damage/heal` в одиночные цели и `effects[]`.
   Лечение получает `includeSelf: true`. Первое обновление не должно молча
   делать все «Инферно» массовыми: изменение цели каждого стандартного навыка —
   отдельная явная правка каталога. Пользовательские определения требуют отчёта
   перехода; плоскую силу нельзя однозначно сохранить при всех характеристиках
   одной новой формулой, нужна калибровка коэффициентов.
4. Включить серверные цели/эффекты, затем UI, NPC и новые бои версии 3.
   Ожидающие комнаты обновлять при старте. Активные v2 и legacy читаются и
   завершаются своим старым обработчиком без новых критов и временных эффектов.
5. После сверки расчётов и интеграционных сценариев сделать v3 стандартом.
   При откате отключать создание v3, сохраняя обработчик уже активных v3;
   откат приложения ниже поддержки v3 запрещён, пока такие бои существуют.

Для активного v2 остаётся `{targetId}` и старый ответ. Для v3 допустим только
`target`; версия схемы определяется серверным снимком боя. Текущие GET каталога
и навыков персонажа должны сохранять старые поля проекции до обновления
клиента; новый контракт добавляет `targeting`, `effects` и рассчитанные
подсказки. Плоская `power` больше не может обозначать итог всего составного
навыка, это поле следует пометить устаревшим, затем убрать отдельной версией API.

Перед реализацией желательно подтвердить: старт и рост характеристик, формулу
защиты/влияние удачи, связь длительности с интеллектом, восстановление ходов
при заморозке и стратегию компенсации старых характеристик. Рекомендуемые
значения уже описаны; ни один из этих вопросов не мешает реализации реестра,
системы целей и обработчиков с конфигурацией. Ответственный за баланс —
владелец проекта. Блокирующих для подготовки спецификации вопросов нет.

## Критерии реализации

| Требование / риск | Проверка | Ожидаемый результат |
| --- | --- | --- |
| Шесть видов цели | Unit + REST + браузер, включая бой 1×1 и командный | Правильные участники/клетка, никаких лишних целей |
| Самолечение и выбор союзника | `includeSelf` true/false | Себя можно выбрать только явно разрешённым навыком |
| Видимость после всех каскадов | Старые сценарии энергии с новым составным навыком | Только прямые типы; отключённые навыки остаются видны |
| Неверная/погибшая цель и координата | REST с подменённой командой | 400, без расхода энергии, КД и изменений поля |
| Массовый каст с несколькими эффектами | Unit + транзакционный тест | Одна цена, порядок эффектов, победа после полной партии |
| Баф перед ударом в одном касте | Unit | Второй эффект использует исходные характеристики каста |
| Пересчёт и снятие модификаторов | Unit + проверки случайных порядков наложения | Нет дрейфа характеристик, источник виден |
| 2 хода на себя/противника в 3×3 | Unit по локальным счётчикам | Два учитываемых собственных хода, ход наложения исключён |
| Тик убивает активного участника | Unit | Нет действия мёртвого, правильно выбраны следующий/волна/победа |
| Повторное наложение и снятие | Unit всех политик и лимитов | Нет незапланированного немедленного тика или вечного эффекта |
| Щит, защита и крит | Unit с управляемым RNG | Защита, затем поглощение; корректный расход щита и HP |
| Отмена, повтор, гонка двух вкладок | Браузер + PostgreSQL | Отмена бесплатна; один каст, второй 409, RNG не переброшен |
| Ошибка сохранения после эффектов | Интеграционный тест | Полный откат состояния, ресурсов, RNG, награды и outbox |
| Заморозка и поиск хода NPC | Unit + браузер на прямоугольном поле | Ручная перестановка запрещена всем, каскады работают |
| Заморозка закрыла последний ход | Unit | Снятие старых ограничений восстанавливает ход без энергии |
| Перезапуск и отключённый WS/Redis | PostgreSQL/MongoDB/Redis + REST | Те же эффекты и сроки, управление через REST |
| Расширение реестра и старые данные | Миграционные тесты | Новый ID работает, повтор миграции безопасен, прогресс сохранён |
| Старые активные бои | Регрессия v2 и legacy | Старые формулы, цели, цена и поведение сохранены |

При реализации обязательны обычный `pnpm check`, интеграционные проверки
из README и браузерный сценарий выбора участника/клетки. Процент покрытия
сам по себе не заменяет перечисленные проверки поведения.
