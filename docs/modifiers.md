# Общие допы: сила, применимость и вероятности

Статус: реализованы формат допов v1, уровень предмета, взвешенный крафт,
опорные величины навыков и индивидуальные вероятности. Зелья с составными
эффектами, камни и боевые trigger оружия остаются отдельными будущими этапами.
Текущая реализация и её ограничения описаны в [аудите](architecture/GAME_MECHANICS_AUDIT.md).

Реализованные правила:

- Ранг предмета определяет количество допов; уровень предмета — их величину.
- У допа есть опорная величина и диапазон генерации; навык использует опорную
  величину со своими коэффициентами и может учитывать характеристики персонажа.
- Доп содержит отдельные поля разрешённых применений: оружие, броня, навыки,
  зелья, бафы и другие явно поддержанные категории.
- У каждого допа отдельно настраиваются шанс выбора при крафте и шанс
  срабатывания при применении. Это разные параметры и разные броски.
- Шанс срабатывания может расти с уровнем навыка, но рост не обязателен.

Документ — канонический источник общего определения допа, областей применения,
двух вероятностей и правил сохранения. [Развитие предметов](item-progression.md)
определяет уровень/ранг и крафт; [эффекты навыков](skill-effects.md) — цели,
последовательность, длительность и стэки; [характеристики](character.md) —
операции и пересчёт. Общий каталог по-прежнему принадлежит `effects`, вещи —
`inventory`, активные эффекты — агрегату `battles`.
Профили силы от itemLevel относятся к каталогу `items`, параметры рангов
навыка — к `skills`; `content` собирает один согласованный снимок всех каталогов.

## Определение допа

Поля `ModifierDefinition` с `formatVersion: 1`:

| Поле | Смысл |
| --- | --- |
| `id`, `version`, `name` | Стабильная идентичность и версия определения |
| `statId`, `operation` | Изменяемая характеристика и поддержанная операция |
| `baseValue` | Опорная величина в единицах операции |
| `itemRoll.minFactorBps`, `itemRoll.maxFactorBps` | Диапазон множителей опорной величины при генерации вещи; 10000 = ×1 |
| `itemRoll.scalingProfileId` | Версионируемая кривая силы от уровня предмета |
| `craftWeight` | Неотрицательный целочисленный вес выбора этого допа в крафтовом пуле; 0 исключает выбор |
| `activationChanceBps` | Базовый шанс срабатывания при применении, 0–10000 |
| `allowWeapon`, `allowArmor`, `allowSkill`, `allowPotion`, `allowBuff`, `allowDebuff`, `allowGem` | Независимые булевы разрешения |

Схема реализована в `core/modifiers.ts`; старые minValue/maxValue читаются
только для совместимости. Диапазон через коэффициенты выбран, чтобы `baseValue` и независимо заданные min/max
не расходились при балансировке. Например, `baseValue=10` и 8000–12000 означают
опорный диапазон 8–12. `Content.modifierRulesVersion: 1` включает новую
генерацию и вероятности, `ItemQuality.version: 1` фиксирует новую модель вещи.

`baseValue` — знаковое целое; единица `add_flat`/`set` определяется statId,
`add_percent`/`multiply` измеряются в базисных пунктах. Это не общий безразмерный
коэффициент для всех характеристик. Ранги и уровни не меняют statId/операцию.

`itemRoll` обязателен для определения, разрешённого генератору экипировки;
у определения, разрешённого только навыкам, он может отсутствовать, а
`craftWeight` должен быть 0. Конкретные технические границы величин и уровней
задаются валидированной схемой и профилем, а не клиентским запросом.

## Где разрешено использовать доп

| Поле | Разрешённое применение |
| --- | --- |
| `allowWeapon` | Доп оружия |
| `allowArmor` | Доп брони/аксессуара, отнесённого каталогом к этой категории |
| `allowSkill` | Включение в исполняемый состав навыка |
| `allowPotion` | Включение в состав применяемого зелья |
| `allowBuff` | Наложение как временного усиления |
| `allowDebuff` | Наложение как временного ослабления |
| `allowGem` | Свойство камня при будущей реализации камней |

Разрешения задаются отдельными boolean, без битовой маски или второго списка
категорий. Новые поля при техническом расширении получают false; перед
публикацией новой версии они заполняются по фактическим прежним назначениям,
включая существующие бафы/дебафы навыков. Прежние три флага сохраняются.
Полное новое определение должно задавать
все поля явно. Все false запрещают новые назначения, не удаляя старые снимки.

Источник и форма применения — разные проверки. Баф от навыка требует
`allowSkill && allowBuff`; дебаф от зелья — `allowPotion && allowDebuff`.
Постоянный бонус оружия требует allowWeapon и не требует allowBuff.
Баф от зелья проверяется при использовании, а не при простом хранении бутылки.
Нейтральный временный эффект не получает разрешение автоматически: политика
такой категории должна быть явно определена до её использования.

Сопоставление групп предметов разрешениям принадлежит серверному каталогу.
Новая группа не становится оружием только из-за наличия equipSlot. Флаг не
регистрирует обработчик: allowPotion/allowGem сами по себе не реализуют новые
зелья/камни. Неизвестный способ применения отклоняется при публикации контента.
Для новой реальной категории добавляется явное поле и проверка; универсального
`allowAnything` не должно быть.

## Величина на вещи и в навыке

Для аддитивного допа предварительный диапазон вещи:

```text
K = itemScalingProfile(itemLevel)
A = baseValue × minFactorBps / 10000 × K
B = baseValue × maxFactorBps / 10000 × K
minValue = floor(min(A, B))
maxValue = floor(max(A, B))
rolledValue = uniformInteger(minValue, maxValue)
```

Сортировка границ нужна также отрицательным допам. Ранг, уровень персонажа,
профессия и заточка в эту формулу не подставляются. Профессия сохраняет роль
в выборе ранга; новый способ влияния на силу требует отдельного решения.
Пример, не утверждённый баланс: baseValue=10, разброс ×0.8–1.2, K=2 дают 16–24.

Рост не обязан быть линейным. У плоских величин и процентов могут быть разные
профили и пределы; вероятность и длительность не умножаются на itemLevel.
Для `multiply` масштабируется отклонение от нейтрального 10000, например
`10000 + (baseValue − 10000) × K × factor`, а не весь множитель 12000 целиком.
`set` требует подходящего профиля и явных границ. Неподдержанную комбинацию
операции/профиля отвергать до генерации. Коэффициенты вычислять целочисленно
или рационально; округление и ограничения должны быть версионированы.

Назначение допа навыку содержит `modifierDefinitionId`/версию и параметры
силы: `coefficientBps`, необязательный `coefficientPerSkillRankBps` и, при
необходимости, существующее выражение от caster/target. При заданном coefficientBps расчёт:

```text
coefficient(r) = coefficientBps + (r − 1) × coefficientPerSkillRankBps
value(r) = floor(baseValue × coefficient(r) / 10000 + attributeContribution(r))
```

Коэффициент должен оставаться в разрешённых границах на всех рангах. Отсутствие
прироста означает 0; для multiply применяется то же правило нейтрального
значения. Все слагаемые обязаны иметь совместимые единицы. Ранг навыка здесь
не является рангом качества предмета. Предметный диапазон при обычном касте
не разыгрывается; отдельный случайный разброс навыка в это решение не входит.
Существующие damage/heal остаются типизированными эффектами со своими формулами:
общий каталог статовых допов не превращается автоматически в обработчик урона.

Пример назначения общего допа физической мощи в составе навыка (при
baseValue=10):

```json
{
  "id": "power-buff",
  "kind": "stat_modifier",
  "modifierDefinitionId": "physical-power",
  "modifierDefinitionVersion": 1,
  "recipient": "selected",
  "polarity": "buff",
  "statId": "physicalPower",
  "operation": "add_flat",
  "coefficientBps": 5000,
  "coefficientPerSkillRankBps": 500,
  "magnitude": {"unit": "points", "constant": 0},
  "durationTurns": 2,
  "activationChanceBps": 3000,
  "chancePerSkillRankBps": 200,
  "maxChanceBps": 5000
}
```

На первом ранге величина +5, шанс 30%; рост независим. `magnitude` добавляет
вклад от характеристик, здесь он нулевой. Без coefficientBps сохраняется
действующий расчёт только по magnitude; новые поля не переписывают прежние навыки.

## Шанс выбора при крафте

Шанс выбора хранится в `craftWeight`: относительный вес,
а не независимый бросок «доп выпал/не выпал». Крафт обязан выдать ровно N допов
по рангу, поэтому независимые Bernoulli-броски с произвольными процентами
не обеспечивают согласованное количество. Это объяснение выбранного алгоритма,
не изменение требования об индивидуальной редкости каждого допа.

Алгоритм каждого слота:

1. Построить совместимый пул по области применения, наличию itemRoll и
   положительному craftWeight. Использовать стабильный порядок ID.
2. Выбрать определение с вероятностью `weight / sum(remainingWeights)`.
3. Удалить выбранный ID из пула; повторов определения на вещи нет.
4. Рассчитать и разыграть величину по уровню предмета, сохранить её в черновике.
5. Повторить до количества, заданного рангом.

При весах 20 и 10 первый кандидат вдвое вероятнее второго на конкретном выборе.
Это не означает 20% и 10% итогового присутствия на вещи: оно зависит от пула
и количества допов. При выборе всех допустимых кандидатов каждый попадёт
в результат независимо от относительной редкости. Если нужны жёсткие ограничения
присутствия редкого допа, потребуется отдельно согласованное правило пула.

Положительных совместимых кандидатов должно хватать на N. Иначе публикация
профиля/рецепта отклоняется; при обнаружении ошибки во время команды откатывается
весь крафт. Не уменьшать число допов молча и не подставлять запрещённый доп.
Ранг common с N=0 не выполняет броски выбора/величины допов.
Все равные веса сохраняют нынешний равномерный выбор. Общий шанс успеха
эксперимента и распределение ранга профессией остаются отдельными механизмами.

## Шанс срабатывания при применении

`activationChanceBps` каждого определения независимо от craftWeight задаёт
базовый шанс выполнить соответствующий доп. У экземпляра вещи сохраняется
снимок этого поля. Назначение навыку может задавать собственный базовый шанс
как явный override, `chancePerSkillRankBps` и `maxChanceBps`:

```text
base = assignment.activationChanceBps ?? definition.activationChanceBps
chance(r) = clamp(base + (r − 1) × chancePerSkillRankBps, 0, maxChanceBps)
```

Неуказанный прирост = 0, неуказанный предел = 10000. Значения целые, изменение
200 bps означает +2 процентных пункта, а не относительные +2%. Пример настройки:
30% с +2 п.п. за ранг, предел 50%; другой доп имеет 30% без роста.
Процентная сила допа, шанс срабатывания и шанс критического удара — разные поля.
Проверка вероятности применяется общей оболочкой исполняемого эффекта; ссылка
на ModifierDefinition нужна для статового допа, но не обязательна для damage,
heal или dispel. Эти инструкции могут иметь свои явные параметры вероятности
с default 100%, сохраняя собственный тип и формулу величины.

Для применяемого эффекта выполняется отдельный бросок на
`effectAssignmentId × targetId` в принятом действии, порядок — индекс эффекта,
затем стабильный ID получателя. `recipient: caster` разыгрывается один раз.
Несколько ударов как разные инструкции имеют свои броски. Совместное
срабатывание нескольких инструкций или один общий бросок на группу требуют
явной будущей policy; скрытую корреляцию не вводить.

Сначала проверяются команда, цели и ресурсы; затем на черновике фиксируются
расходы и рассчитанные до каста величины. При обработке каждой допустимой живой
цели производится проверка шанса, при успехе применяется эффект. 0% всегда
пропускается, 100% всегда применяется — оба случая не расходуют RNG. Для
промежуточного шанса `roll(10000) < chanceBps`. При неудаче только этого допа
следующие инструкции продолжаются, энергия/расходник и cooldown не возвращаются.
Несработавший урон не выполняет отдельный критический бросок.

Уже наложенный баф/дебаф продолжает действовать до срока без повторного броска
при чтении, пересчёте или каждом ходе. Повторный каст снова проверяет шанс;
неудача не обновляет срок и стэки существующего экземпляра. У постоянного
источника экипировки шанс применения должен быть 100%: не бросать монету при
надевании или пересчёте. Доп с шансом меньше 100% на оружии требует явного
поддержанного боевого trigger; система таких trigger пока не реализована и
не появляется автоматически от allowWeapon.

## Сохранение, повтор и совместимость

- Определение содержит version в effects; навык может закреплять её через
  modifierDefinitionVersion. Бой сохраняет полный снимок контента; старые
  активные бои не читают новую запись определения. Исторические версии
  каталогов отдельной коллекцией пока не публикуются.
- `ItemInstance` сохраняет itemLevel, definitionRef и снимки допов: ID/версию,
  операцию/statId, конечную величину и activationChanceBps. Метаданные генерации
  включают версию профиля и рассчитанные границы, чтобы результат можно было
  объяснить. craftWeight не является вероятностью будущего применения.
- При смене владельца, надевании, чтении, перезапуске и повторе квитанции не
  перебрасываются ни набор, ни величины. Изменение веса влияет на новые крафты.
- В бою сохраняются RNG, результат действия и только успешно созданные
  ActiveEffect. Журнал/результат должен различать `applied`, `chance_failed`,
  `skipped_dead_target`; RNG state не выдаётся публичным DTO.
- Ошибка обработчика или сохранения откатывает весь черновик боя, включая RNG
  и затраты. После commit повтор запроса не выполняет новые броски.
- Существующие вещи и активные бои сохраняют старые версии расчёта. Переход
  не перебрасывает допы и не добавляет им вероятность задним числом.

Серверный preview нового контента должен отдавать рассчитанный диапазон для
itemLevel и итоговый шанс применения для ранга навыка. craftWeight можно
показывать как относительную редкость; выводить его числом процентов вероятности
получить доп на готовой вещи нельзя. Клиент не рассчитывает броски и не выбирает
разрешающую категорию. Действующие REST-пути сохранены: каталог крафта отдаёт itemLevel и
modifierPreviews с диапазоном/весом/вероятностью, а skillChoices.effectPreviews —
итоговый activationChanceBps. Интерфейс показывает эти серверные значения.

Базовые определения v1 создаются сразу с `version: 1`, `formatVersion: 1`,
опорными величинами и всеми булевыми разрешениями. Нет преобразования прошлых
вариантов каталога. Все веса по умолчанию 100, вероятность 100%, рост 0.

MongoDB itemScalingProfiles принадлежит items: flat-stat задаёт
`min(100000, 10000 + (itemLevel − 1) × 1000)` bps, percentage —
`min(20000, 10000 + (itemLevel − 1) × 100)` bps, fixed — 10000 bps.
Профили редактируются как данные, seed не перезаписывает настроенные записи.
Уровень определения предмета — целое 1–1000; отсутствующее значение каталога
при обновлении получает 1. Это исходные консервативные настройки, не рост
уровня вещи от опыта героя.

Единственная PostgreSQL-миграция `init` сразу создаёт `item_level` (1–1000)
и `definition_version` (>0), оба NOT NULL с базовым значением 1. `quality`
остаётся nullable для вещей без рангового результата. Качество v1 содержит
itemLevel и baseSnapshot, допы — конечную величину, профиль/версию, границы
и activationChanceBps. При изменении базовой схемы пересоздаются локальные тома.

При старте нового боя сервер задаёт скрытый начальный RNG для новых правил;
вероятности используют сохраняемый поток attributeRngState. REST/WS удаляют
это поле из ответа; outbox и архив сохраняют внутренний снимок целиком.
Это поток вероятностей/критов, не полный replay поля: генерация поля по-прежнему
использует существующий механизм. Проверки — pnpm check, test:migrations и
test:infrastructure; интеграционные тесты работают с временными базами.

## Приёмка и оставшиеся настройки

| Сценарий | Проверяемое поведение |
| --- | --- |
| Два ранга одной вещи одного уровня | Ровно заданное каждым рангом число допов; одинаковый диапазон общего допа |
| Два уровня при равном ранге | То же количество; диапазон меняется только по профилю уровня |
| Доп разрешён навыку, но запрещён бафам | Публикация назначения как бафа отклонена |
| Нулевой craftWeight | Доп не выбирается; прочие области применения возможны |
| Разные веса | Границы weighted-roll соответствуют условным вероятностям каждого слота |
| Не хватает совместимого пула | Ошибка контента/полный rollback, а не недобор допов |
| 0%, 100% и граничный activation-roll | Предсказуемые исходы и количество потреблённых RNG-значений |
| Рост вероятности отсутствует/ограничен | 0 прироста либо корректный cap, без влияния itemLevel/ранга вещи |
| Один доп не сработал, следующий гарантирован | Второй выполняется, общая цена остаётся списанной |
| Неудачное повторное наложение | Прежние величина, срок и стэки бафа не меняются |
| Ошибка последнего эффекта/SQL save | Состояние, затраты и RNG откатываются вместе |
| Потерянный ответ, reload, старый snapshot | Сохранённый результат восстанавливается без новых бросков |

Конкретные уровни новых определений, базовые величины, редкости, шансы и рост
каждого допа настраиваются каталогом. Текущие навыки сохраняют 100% до явной
настройки; наличие полей не меняет баланс автоматически. Вариативные уровни
выхода рецепта, proc-триггеры оружия, новые виды зелий, камни и персональные
правила neutral требуют отдельного этапа с поддержанными обработчиками.
