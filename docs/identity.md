# Аккаунты и выбор персонажа

Статус: реализованный упрощённый вход базовой v1. Пользователь явно выбрал
аккаунты без пароля. Полноценная регистрация, подтверждение личности и
восстановление доступа в этот этап не входят.

## Игрок и владение

`Account.id` — стабильная идентичность игрока (`playerId` будущего чата).
У аккаунта может быть несколько персонажей. `characters.account_id` должен
быть обязательной ссылкой на аккаунт; домен characters владеет этой связью.
Поле `Character.accountId` — её проекция в общих данных. Канонический владелец
инвентаря по-прежнему персонаж, а не аккаунт: `InventoryContainer.ownerId` и
`ItemInstance.ownerId` равны `Character.id`.

Готовая `init` создаёт аккаунты «Игрок 1» и «Игрок 2», по пять героев 10-го
уровня у каждого. Новый аккаунт создаётся по имени и начинает без персонажей;
из его экрана можно создать несколько героев обычным атомарным сценарием
создания персонажа и рюкзака. Имя аккаунта: 2–32 символа после обрезки пробелов,
уникально без учёта регистра. Присвоить владельца нового героя через тело
запроса нельзя: он берётся из сессии.

Аккаунт на данном этапе выбирается из публичного списка без пароля. Это
согласованный режим прототипа: любой посетитель может выбрать любой аккаунт.
Сессия разграничивает данные выбранных аккаунтов и запросы, но такой выбор
не подтверждает, что перед нами настоящий владелец учётной записи.

## Порядок экранов

1. При отсутствии действующей сессии должно открываться окно выбора аккаунта.
   Там доступны список аккаунтов и создание нового по имени.
2. Выбор аккаунта должен создавать новую сессию с `characterId: null` и
   открывать отдельную страницу выбора персонажа именно этого аккаунта.
3. Страница должна показывать карточки своих героев, их тип, уровень и свободные
   очки развития. Чужие персонажи не должны присутствовать в списке.
4. Выбор карточки должен сохраняться сервером и открывать игру. Создание героя
   должно обновлять список, оставаясь на странице выбора до явного выбора героя.
5. В игре должны быть доступны «Персонажи» и «Сменить аккаунт». Первое действие
   очищает выбранного героя сессии; второе отзывает сессию и возвращает к аккаунтам.

Новая сессия не должна автоматически выбирать первого или ранее выбранного
героя. При перезагрузке действующей вкладки сервер должен восстановить текущий
выбор. Ссылка на бой или экран инвентаря сохраняется в hash-навигации, но не
должна обходить оба этапа выбора. Выход из интерфейса боя не является сдачей
и не останавливает серверный таймер.

Токен хранится в `sessionStorage` вкладки. Разные сессии могут выбирать разные
аккаунты и персонажей. При смене аккаунта представления игры должны
размонтироваться, подписки закрываться, а данные прошлого аккаунта не должны
показываться в новой сессии. Истёкшая/отозванная сессия при ответе 401 возвращает
к выбору аккаунта. Поздний ответ старого токена не должен завершать новую сессию.

## API

| Метод и путь под `/api/v1` | Доступ и результат |
| --- | --- |
| `GET /accounts` | Без сессии; публичные `id`, `name`, `createdAt` |
| `POST /accounts` | Без сессии; `{name}` создаёт аккаунт, повтор имени — 409 |
| `POST /identity/session` | Без сессии; `{accountId}` выбирает аккаунт и возвращает токен, аккаунт, `characterId: null`, `expiresAt` |
| `GET /identity/session` | Текущий аккаунт, выбранный герой или null, срок сессии; без раскрытия токена |
| `POST /identity/session/character` | `{characterId: UUID | null}`; только свой герой, null возвращает к выбору |
| `DELETE /identity/session` | Отзывает текущий токен, возвращает `{ok: true}` |
| `GET /characters` | Только персонажи аккаунта из сессии |
| `POST /characters` | Создаёт героя и имущество для текущего аккаунта одной транзакцией |

Остальные HTTP-маршруты требуют `Authorization: Bearer <token>`. Нет токена,
он неверен, отозван или истёк — 401. Попытка выбрать/прочитать/изменить чужого
персонажа либо его имущество — 403. Неверная схема входа — 400, неизвестный
аккаунт при выборе — 404. Ошибка не должна менять прежний выбор героя.

Проверки распространяются на характеристики, навыки, крафт, инвентарь,
передачу между своими героями и команды создания/вступления/старта/действий боя.
Обе стороны ручной передачи и объединения стэков должны принадлежать текущему
аккаунту. Доступ к предмету проверяется заново при чтении экземпляра, а при
изменении — внутри транзакции под блокировками владельцев. Ключ повтора команды
инвентаря из HTTP должен учитывать аккаунт инициатора.

Бои и лобби доступны как общие игровые представления авторизованных сессий;
боевые карточки и снимки предметов участников сохраняют правила публичного
просмотра из [combat.md](combat.md). Это не открывает постоянный чужой рюкзак.
Socket.IO `watch` требует токен сессии в `handshake.auth.token`; клиент должен
закрывать подписку при выходе из игры/смене аккаунта.

## Хранение и архитектура

Модуль `identity` владеет таблицами `accounts` и `account_sessions`; все они
создаются в единственной `init`. `characters.account_id` принадлежит модулю
characters и индексируется для выборки своего списка. Состояние боя и инвентаря
не переносится в identity.

Сессия получает случайный 256-битный токен. В БД должен храниться только его
SHA-256, `account_id`, выбранный `character_id` или null и `expires_at`.
Срок — 7 суток с создания, без неявного продления чтениями. Хеши и токены не
должны попадать в список аккаунтов, персонажей, события боя и технические логи.
Сессии хранятся в PostgreSQL и переживают перезапуск процесса. Автоматическая
периодическая очистка истёкших строк пока не реализована; истечение доступа
проверяется каждым запросом.

`IdentityService` обращается к своему порту и публичному `CharactersService`.
`IdentityAccessModule` связывает общий HTTP guard с identity, characters и
inventory без циклических зависимостей. Контроллеры объявляют проверяемые
ресурсы через metadata, `CurrentAccount` получает уже проверенный контекст.
Доменным задачам, таймерам и наградам не нужна пользовательская сессия: они
работают через доверенные application-сервисы. Подключения и SQL остаются
в адаптерах; [механизм guards NestJS](https://docs.nestjs.com/guards) применяется
на транспортной границе.

## Проверка и дальнейшее развитие

Проверяются выдача/хеширование/истечение/отзыв токена, независимые сессии,
переход к выбору героя, восстановление выбора, создание пустого аккаунта,
изоляция списков и отказ всех основных команд с чужими ID. Интеграционные
проверки выполняются в отдельных временных PostgreSQL/MongoDB базах и Redis
namespace. Для нового базового состояния существующей установки необходимо
пересоздать локальные тома по README; автоматический сброс данных не выполняется.

Принятый [проект чата](chat.md) должен использовать аккаунт как `playerId`,
а выбранного принадлежащего ему героя как автора. Чат, друзья, ЧС, группы и
обмен пока не реализованы. Для публичного режима с приватной перепиской позже
потребуется заменить открытый выбор аккаунта проверяемым способом входа.
