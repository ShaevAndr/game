# Друзья и чёрный список

Статус: реализован модуль `social` внутри монолита. Связи относятся к
`Account.id`, поэтому смена персонажа не создаёт новую дружбу или ЧС.
[Чат](chat.md) обращается только к application-сервису модуля.

## Правила

- Дружба требует согласия: заявка видна отправителю как `outgoing`, адресату
  как `incoming`. Адресат может принять или отклонить, отправитель — отменить.
  Друзей можно удалить. Повтор одной операции возвращает прежний результат.
- Встречные заявки сводятся к одной принятой дружбе. При одновременных запросах
  с одной исходной ревизией второй запрос считается согласием на первый.
  Это единственное исключение из проверки ожидаемой ревизии пары.
- ЧС направленный: игрок видит только собственные блокировки. Если блокировка
  есть хотя бы с одной стороны, новые личные сообщения и заявки в друзья
  запрещены обоим. Ответ одинаковый: «Действие недоступно для этого игрока».
  API не выдаёт чужой `blockedBy` и не показывает, кто заблокировал зрителя.
- Блокировка удаляет существующую дружбу и отменяет ожидающую заявку этой пары.
  Разблокировка не восстанавливает их автоматически. Состояния `declined` и
  `cancelled` не хранят отдельную историю: итог пары — `none`, ревизия остаётся.
- Блокировавший не видит входящие сообщения этого игрока в мире, личной ленте
  и «Все», включая уже загруженные. Его собственные исходящие сообщения
  остаются видимыми. Другие зрители продолжают видеть публичные сообщения.
  Разблокировка возвращает доступную историю. Данные сообщения не удаляются.
- Мировая отправка разрешена независимо от ЧС: фильтр применяется у зрителей.
  Группы и обмен будут использовать те же проверки новых приглашений;
  отмена их ожидающих приглашений добавляется вместе с соответствующим модулем.

## REST API

Все пути требуют bearer-сессию и находятся под `/api/v1`.

| Метод | Путь | Контракт |
| --- | --- | --- |
| GET | `/social` | `{revision, visibilityRevision, relationships}` |
| POST | `/social/actions` | `{operationId, targetPlayerId, expectedRevision, action}` → `{relationship, replayed}` |

`relationship` содержит `playerId`, `revision`, `friendship` (`none`, `incoming`,
`outgoing`, `accepted`) и только свой `blocked`. В списке также есть `playerName`,
полученный через `IdentityService`. После снятия отношений запись пары остаётся
с `none`: её ревизия нужна для последующих команд.

Действия: `friend-request`, `friend-accept`, `friend-decline`, `friend-cancel`,
`friend-remove`, `block`, `unblock`. Цель не может совпадать с текущим аккаунтом.
Сервер извлекает действующего игрока из сессии. Принять свою исходящую заявку
нельзя; команду по изменившейся заявке нужно повторить после обновления списка.

Новая операция возвращает 201, точный повтор ключа внутри аккаунта — 200 с
прежним результатом. Другое тело с тем же ключом — 409 `SOCIAL_OPERATION_CONFLICT`.
Устаревшая ревизия — 409 `SOCIAL_CHANGED`; клиент обновляет список и даёт
повторить действие. Неуспешная операция не оставляет квитанцию. Запрет общения —
403 `SOCIAL_NOT_ALLOWED`; невалидная команда/переход — 400, неизвестный игрок — 404.

## Хранение и конкурентность

Единственная миграция `init` создаёт:

| Таблица | Владеет |
| --- | --- |
| `social_players` | UUID игрока, ревизия списка и отдельная ревизия видимости |
| `social_pairs` | Уникальная упорядоченная пара UUID и JSON агрегата: дружба, инициатор, направления ЧС, ревизия |
| `social_operations` | Ключ `(player_id, operation_id)`, сигнатура входа и сохранённый результат |

Квитанция блокируется до выполнения команды. Строки обоих игроков блокируются
в стабильном порядке ID; затем читается и меняется пара. Пара, ревизии игроков
и квитанция сохраняются одной `UnitOfWork`. Прямой SQL к таблицам identity/чата
не используется. Имена аккаунтов даёт публичный сервис identity.

Личная отправка блокирует тех же двух игроков через `SocialService` внутри
транзакции чата и только затем потоки доставки. Поэтому гонка с блокировкой
имеет согласованный исход: сообщение принято до ЧС либо отклонено после него.
Чтение ленты удерживает блокировку зрителя, получает его политику и применяет
её до завершения транзакции. Курсор содержит `visibilityRevision`; при изменении
своего ЧС старый курсор возвращает 410 и клиент перечитывает историю.

Курсоры продвигаются также по скрытым сообщениям, поэтому фильтр ЧС не вызывает
бесконечное перечитывание одной страницы. Страница может содержать меньше
`limit` видимых сообщений; `hasMore` означает наличие непроверенных доставок.
Gateway перед уведомлением проверяет видимость автора. WS не передаёт текст;
авторизованный REST остаётся обязательным источником содержимого.

## Интерфейс

Меню чужого автора содержит действие дружбы по её текущему состоянию,
«Добавить в чёрный список»/«Убрать из чёрного списка» и «Личное сообщение».
Меню открывается кнопкой имени, расположено в пределах экрана, поддерживает
стрелки и Escape, после социального действия возвращает фокус на имя.
Выбор личного сообщения переводит фокус во ввод общей личной ленты.

Вкладка «Игроки» в окне чата показывает входящие/отправленные заявки, друзей и
свой ЧС. Новая входящая заявка отмечается точкой рядом с вкладкой. Здесь можно
принять, отклонить, отменить заявку, удалить друга, снять блокировку или написать.
Списки сверяются через REST каждые 5 секунд и сразу после собственного действия;
отдельный WS для социальных связей не вводится.

Собственная блокировка сразу фильтрует загруженные сообщения. Выбранный адресат
и черновик сохраняются; если адресат в своём ЧС, отправка отключена с объяснением.
Скрытая встречная блокировка проверяется сервером, ошибка сохраняет черновик.
При сетевом сбое неизменённое социальное действие повторяется с тем же ключом;
при 409 клиент перечитывает состояние и создаёт новую команду для нового решения.

Проверки: unit-тесты заявок, встречных команд, ревизий, ЧС и отката;
`test:migrations` и `test:infrastructure` проверяют настоящие PostgreSQL/REST/WS,
гонку отправки с ЧС, продвижение курсора, отсутствие приватных полей и рестарт.
