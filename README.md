# Стихии — Tactical Match-3

Сетевой MVP: общее поле «три в ряд» и пошаговый бой. Node.js 22+, TypeScript, NestJS, React, PostgreSQL + Kysely, MongoDB, Redis, BullMQ, Socket.IO, pnpm workspaces.

Правила структуры и взаимодействия: [архитектура](docs/architecture.md). Доменные правила: [бой и энергия](docs/combat.md), [боевое поле](docs/battlefield.md), [навыки](docs/skills.md), [предметы](docs/items.md), [инвентари](docs/inventory.md). Инструкции для дальнейших изменений: [AGENTS.md](AGENTS.md).

Спроектирован следующий этап навыков: [шесть видов цели, составные эффекты,
бафы, дебафы и длительность](docs/skill-effects.md), [расширяемые характеристики
и производные параметры](docs/character.md). Базовые характеристики: сила,
ловкость, интеллект, выносливость и удача. Это спецификация для реализации;
работающий MVP ниже пока использует механику v2.

## Запуск всего проекта

На новом компьютере установите Git и Docker с Compose (в Windows — запущенный Docker Desktop с Linux-контейнерами). Node.js и pnpm для этого способа не нужны:

```sh
git clone https://github.com/ShaevAndr/game.git
cd game
docker compose up -d --build
```

Откройте **http://localhost:8088**. Compose собирает и запускает frontend, backend, PostgreSQL, MongoDB и Redis. Для просмотра журналов используйте `docker compose logs -f`. Запуск в текущем терминале вместо фона: `docker compose up --build`.

Порт можно изменить через `GAME_WEB_PORT` в `.env`, затем выполнить `docker compose up -d`. Compose автоматически использует этот же порт для `WEB_ORIGIN` сервера. Если в Windows на `localhost:8080` появляется `Access Error: 404 -- Not Found`, проверьте конфликт со сторонним `ApplicationWebServer`: Windows и WSL могут отдавать разные страницы по IPv4 и IPv6. По умолчанию игра использует порт 8088.

Миграции PostgreSQL и первоначальное наполнение MongoDB выполняются при старте сервера. Миграция `003_demo_characters` сразу добавляет десять готовых героев 10-го уровня — по два на каждую ветку, с изученными навыками и зельями. На новом устройстве не нужно создавать персонажей вручную. Данные сохраняются в Docker volumes. Остановить проект: `docker compose down`.

Для обновления существующей установки из папки проекта:

```sh
git pull --ff-only
docker compose up -d --build
```

У каждого компьютера собственные базы и прогресс. Git переносит код и начальные данные миграций; для переноса накопленного прогресса нужны резервные копии баз.

### Разработка с обновлением кода

Для разработки установите также Node.js 22+:

```sh
corepack enable
pnpm install
pnpm infra
# Скопируйте .env.example в .env при необходимости изменить настройки.
pnpm dev
```

Клиент: **http://localhost:5173**, сервер: **http://localhost:3001/api**. Vite и Nginx проксируют HTTP API и Socket.IO; клиент использует тот же origin. PostgreSQL и MongoDB обязательны: скрытой подмены на память нет. Redis используется для кэша и очередей; при временном отказе Redis чтение идёт из MongoDB, а архивирование боёв ожидает восстановления в outbox PostgreSQL.

В Windows при блокировке `pnpm.ps1` используйте `pnpm.cmd`. Если Corepack не может записать глобальные shims, можно установить их локально:

```powershell
New-Item -ItemType Directory -Force .corepack-bin
corepack enable --install-directory .corepack-bin
$env:COREPACK_HOME = Join-Path (Get-Location) '.corepack'
$env:PATH = "$(Join-Path (Get-Location) '.corepack-bin');$env:PATH"
pnpm.cmd install
pnpm.cmd dev
```

## Как попробовать

1. Выберите готового героя 10-го уровня в списке персонажей или создайте своего: выберите тип героя и введите имя. Все персонажи доступны каждому, авторизации и владения нет. Выбор хранится отдельно для каждой вкладки.
2. Для одиночной игры выберите **«Бой с ботом»**, создайте комнату и нажмите «Начать бой». Бот получает характеристики и изученные навыки вашего героя и ходит автоматически, включая лечение при низком здоровье. Можно также выбрать подземелье: три волны противников.
3. Для сетевой проверки создайте дуэль или командную комнату, скопируйте приглашение и откройте во второй вкладке/браузере. Выберите **другого** персонажа, вступите в другую команду, начните бой.
4. Выберите противника нажатием на карточку. Затем нажмите две соседние фишки так, чтобы собрать линию из трёх или более. Невалидная перестановка не тратит ход.
5. При создании комнаты можно задать строки, столбцы и набор типов; по умолчанию поле 8 × 8 с шестью типами: четыре стихии, физическая сила и защита.
6. После всех сокращений выберите навык типа прямого совпадения. Другие типы навыков скрыты; нехватка энергии или перезарядка делает подходящий навык неактивным. Можно сохранить энергию и завершить ход. Прямые сокращения и каскады показываются отдельно. Если ходов нет, поле автоматически обновляется с теми же настройками.

Для игры с другого устройства откройте `http://IP-компьютера:8088` (или порт из `GAME_WEB_PORT`), разрешив этот порт в локальном firewall. В приглашении используйте доступный другим устройствам адрес вместо `localhost`.

## Правила MVP

В новых боях действует единый порядок: **перестановка → все каскады и энергия → выбор одного навыка → следующий участник**. Навык доступен только при прямом совпадении своего типа. Если подходящего изученного навыка нет, ход заканчивается автоматически. Видимые недоступные навыки не мешают завершить ход без применения.

Обычные прямые и вторичные клетки дают по 1 энергии своего типа, максимум **30 отдельно для каждого типа**. Навык списывает свою стоимость; «Удар» стоит **3 физической энергии**, без перезарядки. Вторичные клетки дают только энергию, не открывая навыки. Прямые клетки защиты дают **+10 защиты за клетку до следующего собственного хода**; вторичные дают только энергию защиты, максимум 30. Расход энергии защиты пока не реализован.

Клетки не наносят урон и не усиливают навыки. Урон навыка: `max(1, сила текущего уровня + атака − защита цели − временная защита)`. Лечение ограничено максимумом HP; можно выбрать живого союзника. Коэффициент защиты настраивается в `balance.combat.defensePerTile`.

За ход можно применить один навык **или** зелье. Зелье доступно до обязательной перестановки. Перезарядка `2` блокирует следующие два собственных хода. Погибшие участники пропускаются. Командные бои поддерживают до 3×3 с чередованием команд; подземелье — до трёх игроков против одного противника в каждой волне. NPC соблюдает те же ограничения. Подробнее — [правила боя](docs/combat.md).

**Инстансы изолированы:** HP, энергия, перезарядки и расход предметов живут внутри конкретного боя; персонаж служит шаблоном. Расход зелий и собранная энергия не переносятся в другие бои. Опыт, уровень, характеристики, очки навыков и изученные навыки сохраняются в PostgreSQL между боями. Постоянный инвентарь управляется на отдельном экране; оружие и броня дают бонусы при старте следующего боя. Изменение экипировки или уровня навыка не меняет уже активный бой.

## Уровни и дерево навыков

Откройте вкладку **«Навыки»** в верхнем меню или нажмите на очки навыков в карточке персонажа. Экран доступен напрямую по `/#skills`. Пять веток — огонь, вода, земля, воздух и физическая сила. В каждой ветке **шесть навыков и два типа героя**; рекомендуемые навыки героев и все зависимости показаны на карточках. У огня, воды, земли и воздуха есть отдельные пути атаки и лечения. Физическая ветка предлагает тяжёлые удары, быстрые атаки и «Второе дыхание» для лечения.

| Ветка | Герои и рекомендуемые навыки |
| --- | --- |
| Огонь | Пиромант — «Искра»; Адепт Феникса — «Тепло Феникса» |
| Вода | Хранитель прилива — «Источник»; Маг льда — «Ледяная игла» |
| Земля | Геомант — «Каменный осколок»; Друид — «Сок жизни» |
| Воздух | Заклинатель бури — «Дуновение»; Хранитель ветра — «Дыхание ветра» |
| Сила | Дуэлянт — «Выпад»; Ветеран — «Второе дыхание» |

Тип героя рекомендует направление развития, сохраняя возможность изучать все пять веток. Характеристики одинаковые. Новый персонаж любого типа, включая «Странника», получает уровень 1, 0 опыта, **4 свободных очка навыков** и только физический «Удар» первого уровня. Профильные навыки изучаются отдельно.

Для изучения сервер одновременно проверяет:

- достаточное количество очков навыков;
- все навыки из `learning.prerequisites`;
- минимальный уровень `learning.level`;
- минимальные характеристики `learning.stats`.

Уже изученный навык нельзя купить повторно. Его можно улучшить до **10-го уровня**: по умолчанию 1 ОН за улучшение и +2 силы за каждый уровень. Настройки хранятся в `skills.progression`. Свиток может выдать неизвестный навык уровня 1 без расхода очков; известный навык он не повышает. Стоимость изучения `learning.pointCost` отличается от затрат энергии на применение в бою. Очки списываются и навык сохраняется под блокировкой строки персонажа в одной транзакции: две вкладки не могут потратить одно и то же очко.

Награда за победу по умолчанию: **100 XP** за бой с ботом или дуэль, **140 XP** за командный бой, **240 XP** за полное прохождение подземелья. Каждый персонаж победившей команды получает полную награду, включая выбывших союзников. Проигравшие и NPC опыта не получают; за отдельную волну награда не выдаётся. Завершённые до обновления бои не награждаются задним числом.

Порог следующего уровня: `100 + (текущий уровень − 1) × 50`. Остаток опыта сохраняется; за одну победу можно получить несколько уровней. Каждый уровень даёт **2 очка навыков**, **+12 HP**, **+2 атаки**, **+1 защиты**. Лимит энергии остаётся 30. Настройки находятся в MongoDB: `settings`, документ `id: balance`, поле `progression`.

Завершение боя, запись наград и развитие победителей сохраняются одной транзакцией. В таблице `battle_rewards` первичный ключ `(battle_id, character_id)` запрещает повторное начисление. Строки персонажей блокируются в одинаковом порядке, поэтому награды из разных боёв и изучение навыков не затирают друг друга.

При старте боя набор и уровни навыков, характеристики с бонусами экипировки обновляются из персонажей, после чего фиксируются в инстансе. Изучение в другом окне не меняет уже активный бой. Старые персонажи получают недостающие поля развития без сброса уровня, характеристик и инвентаря; недостающие настройки MongoDB добавляются при запуске сервера без перезаписи существующих правок.

## Предметы и инвентари

Откройте вкладку **«Инвентарь»** (`/#inventory`). Реализованы группы «Оружие», «Экипировка», «Зелья», «Ресурсы» и «Свитки». Группы хранятся в MongoDB `itemGroups`; новую группу с существующими действиями можно добавить без изменения кода.

Можно создавать контейнеры, читать описание экземпляра, удалять количество, убирать предмет вне контейнера, класть обратно, переносить между контейнерами и персонажами, разделять и объединять стэки. Для оружия и брони доступны экипировка/снятие, для свитков — чтение с выдачей навыка. Зелья используются на экране боя. Выдача новых предметов и навыков — серверные операции для наград и сценариев, без бесплатной клиентской команды.

Новые герои получают меч, броню, руду и свиток вместе с зельями. Имущество существующих героев сохраняется миграцией `005_inventories`. Все мутации требуют `operationId`; повтор запроса не дублирует эффект. Подробные REST-команды и ограничения — в [документе инвентаря](docs/inventory.md). Предложения по ключам, квестовым предметам, трофеям, ремонту, зачарованию и крафту — в [документе предметов](docs/items.md).

## Готовые персонажи и миграции

В миграции `apps/server/src/infrastructure/database/migrations/003-demo-characters.ts` используются фиксированные данные из соседнего JSON-файла. Это настоящий прогресс 10-го уровня: 228 HP, 26 атаки, 12 защиты, после миграции `006_matched_combat` лимит энергии 30. У каждого героя изучена своя ветка (6–7 навыков вместе с базовым «Ударом»), после обновления остаётся 14–16 очков для других веток. Искра и Феникс представляют огонь, Прилив и Иней — воду, Гранит и Ива — землю, Шторм и Зефир — воздух, Клинок и Оплот — физическую силу.

Миграция выполняется автоматически и учитывается в истории Kysely. Фиксированные UUID и `ON CONFLICT DO NOTHING` предотвращают дублирование и сохраняют уже изменённые имена, опыт и навыки. Миграция `006_matched_combat` один раз добавляет существующим героям 2 очка и ограничивает энергию 30, сохраняя навыки и их уровни. Уже активные бои завершаются по прежним снимкам, новые и ожидающие при старте используют v2. Новые персонажи, созданные через интерфейс, начинают с уровня 1. Бой с ботом не требует второго персонажа или второй вкладки; характеристики и навыки соперника фиксируются при старте, и NPC не получает опыт.

## Архитектура

```text
apps/server/src/
  modules/      домены: characters, skills, items, inventory, battles,
                rewards, battle-history, content, battlefield
    <domain>/
      http/          REST-контроллеры и WS gateway
      application/   сценарии и бизнес-сервисы
      ports/         заменяемые контракты хранения и интеграций
      repositories/  PostgreSQL/MongoDB-адаптеры
      *.module.ts    только сборка зависимостей NestJS
  infrastructure/    подключения к PostgreSQL, MongoDB, Redis, BullMQ; миграции
  shared/            контракты транзакций, кэша, очереди; HTTP-фильтры
apps/web/src/
  app/          сборка приложения, навигация и общие действия
  features/     characters, skills, items, inventory, content, arena, battles, battlefield
    <feature>/  api/ (REST), model/ (хуки), components/ (представление)
  shared/       HTTP-клиент и общие UI-примитивы
packages/core/  чистые типы, Zod-схемы, модуль battlefield, движок боя и правила развития
scripts/        автоматическая проверка границ архитектуры
docs/          архитектурные правила и потоки данных
deploy/        Nginx для Docker
```

Самостоятельный модуль поля: [контракт и примеры](docs/battlefield.md). Он принимает квадратный/прямоугольный размер и массив типов; ход возвращает обновлённую матрицу, `direct`, `generated`, `total` и этапы сокращений.

Сервер — единственный источник состояния. Команды проверяют текущего участника, фазу, ресурсы, цели и версию. Изменение инстанса выполняется в транзакции PostgreSQL с `SELECT … FOR UPDATE`; устаревшая версия возвращает HTTP 409. После коммита сервер отправляет снимок в Socket.IO-комнату. Клиент переподписывается и перечитывает снимок после переподключения. При недопустимом действии транзакция откатывается, включая действия NPC.

В JSONB инстанса сохраняются поле, его размер/набор типов, отчёты `boardMoves`, участники с характеристиками, HP, энергия, инвентарь, навыки, перезарядки, очередь, фаза, режим, волна, журнал и **снимок контента**. Активные бои переживают перезапуск сервера. PostgreSQL также хранит версии и историю миграций Kysely.

Текущая конфигурация рассчитана на **один экземпляр NestJS** с фоновыми обработчиками в том же процессе. Redis для очередей и кэша сам по себе не масштабирует WS. При горизонтальном масштабировании нужен общий Socket.IO adapter (например Redis) для доставки событий между процессами. Таймера хода, автоматического поражения при отключении и подбора соперников в MVP нет.

## Изменение контента без изменения кода

База MongoDB: `elemental_tactics`.

| Коллекция | Что хранится |
| --- | --- |
| `skills` | Стихия, стоимость энергии, сила, эффект, перезарядка; `progression`: 10 уровней, цена улучшения и прирост силы; `learning`: цена изучения, уровень, зависимости, характеристики и признак стартового навыка |
| `items` | Определения: группа, лимит стэка, лечение, слот/бонусы экипировки или навык свитка |
| `itemGroups` | Расширяемые группы и поддержанные действия |
| `enemies` | Характеристики и набор навыков NPC |
| `characterTemplates` | Типы героев: имя, описание, ветка и `skillId` начального навыка первого уровня; его требования должны быть доступны новому персонажу |
| `settings` (`id: balance`) | Начальные характеристики, предметы, `combat`: версия, лимит 30, энергия за клетку 1, коэффициент защиты; размер команды, волны; `progression`: награды XP, пороги уровней, очки и прирост характеристик |

Например, изменить силу огненного шара:

```sh
docker compose exec mongo mongosh elemental_tactics --eval 'db.skills.updateOne({id:"fireball"}, {$set:{power:30}})'
```

В PowerShell удобнее открыть интерактивно `docker compose exec mongo mongosh elemental_tactics`, затем выполнить `db.skills.updateOne({id: 'fireball'}, {$set: {power: 30}})`.

Агрегированный `/api/content` кэшируется на 30 секунд. При старте боя, создании персонажа и изучении навыка сервер читает свежие данные MongoDB, обходя кэш. Для немедленного обновления каталога можно удалить ключ `game:cache:content:v1` в Redis (с учётом `REDIS_NAMESPACE`). Изменения контента фиксируются при старте боя; активные инстансы сохраняют свои снимки. Начальные характеристики применяются к новым персонажам, текущие требования изучения — к новым покупкам навыков. Seed использует `$setOnInsert`. Переход на боевую механику v2 один раз обновляет стартовые очки, ёмкость энергии, рост ёмкости и стоимость прежнего бесплатного «Удара», а недостижимые требования ёмкости выше 30 снижает до 30. Описания стандартных шаблонов обновляются только при точном совпадении с прежним текстом. Остальные правки контента сохраняются. Контент проверяется Zod-схемой: отрицательные стоимости, отсутствующие противники волн, неизвестные зависимости и циклы в дереве запрещены. Нужен один стартовый физический атакующий навык без требований и перезарядки со стоимостью до 3; цены навыков — от 1 до 30 энергии. Начальные данные находятся в `packages/core/src/content.ts`.

## API

| POST | `/api/characters/:id/skills/:skillId/upgrade` | Улучшение `{expectedLevel}` |
| GET | `/api/content` | Валидированный каталог MongoDB, кэш до 30 секунд |
| GET | `/api/characters/:id` | Актуальный персонаж |
| GET | `/api/skills`, `/api/skills/:id` | Каталог / описание навыка |
| GET | `/api/items`, `/api/items/:id` | Каталог / описание предмета |
| GET | `/api/characters/:id/inventory` | Стэки основного рюкзака с описаниями |
| GET | `/api/characters/:id/inventories` | Контейнеры, экземпляры, группы и действия |
| GET | `/api/items/groups` | Расширяемые группы предметов |
| GET | `/api/item-instances/:id` | Конкретный экземпляр и действия |
| GET / POST | `/api/battles` | Список / создание `{name, characterId, kind, battlefield?}; старый `rule` принимается, новые бои используют `on-match` v2` |
| GET | `/api/battles/:id` | Снимок инстанса |
| POST | `/api/battles/:id/join` | `{characterId, team: 0 или 1}` |
| POST | `/api/battles/:id/start` | `{characterId, version}` |
| POST | `/api/battles/:id/actions` | `{characterId, version, action}` |

Варианты `action`: `{type:'swap', from:{row,col}, to:{row,col}, targetId?}`, `{type:'skill', skillId, targetId}`, `{type:'item', itemId}`, `{type:'end'}`. Координаты от 0 до соответствующего размера поля минус 1. `Battle.boardMoves` содержит отдельные результаты игроков и NPC: прямые сокращения, каскады и суммы по типам. Основной транспорт — REST, включая все боевые команды. Socket.IO используется только при открытом бое: отправить `watch` с ID боя и дождаться acknowledgement, получать `battle` со снимками, отправить `unwatch` при выходе. Событие `rooms-changed` удалено; лобби загружается через REST раз в 5 секунд и по кнопке. Открытый бой сразу загружается через REST и сверяется каждые 5 секунд независимо от WS; после переподключения выполняются подписка и повторное чтение. Устаревшие версии снимков игнорируются.

## Redis и фоновые задачи

`pnpm infra` запускает PostgreSQL, MongoDB и Redis. Настройки: `REDIS_URL` и `REDIS_NAMESPACE` (по умолчанию `game`). Compose включает Redis AOF, volume `redis_data` и `maxmemory-policy=noeviction`; кэш и очередь используют разные префиксы. Не применять `FLUSHDB` для сброса кэша: это удалит и задачи.

Очередь BullMQ `battle-archive` сохраняет завершённые бои в MongoDB `battleArchives`. Запись outbox создаётся в той же PostgreSQL-транзакции, что результат и награды; диспетчер проверяет её каждую секунду. Обработка повторяется до 5 раз с экспоненциальной задержкой от 1 секунды. Повторная доставка безопасна благодаря ID задачи и уникальному ID архива. Последние 1000 успешных задач сохраняются; неуспешные остаются для диагностики и ручного повтора. Подробнее о восстановлении и ограничениях — [архитектура](docs/architecture.md#очереди-и-отказы).

Опыт, расход предметов и проверка хода выполняются синхронно в PostgreSQL, а не в очереди. Постоянные переносы, экипировка и свитки сохраняются транзакционно; расход зелий остаётся изолированным внутри боя.

## Проверка

```sh
pnpm check
# Или отдельно: pnpm check:architecture, pnpm typecheck, pnpm test, pnpm build
# При запущенном PostgreSQL: проверка миграций в отдельной временной базе.
pnpm --filter @game/server test:migrations
# При запущенных PostgreSQL, MongoDB и Redis: HTTP, WS, кэш, очередь, архив и shutdown.
pnpm --filter @game/server test:infrastructure
```

Тесты ядра проверяют всех 30 навыков в новой механике: прямые типы, видимость, недоступность, списание энергии после каскадов, лимит 30, временную защиту и её истечение, NPC и зелья. Дополнительно покрыты старые режимы для сохранённых боёв, поле, каскады, десять шаблонов, рост уровней, очки, зависимости и уровни навыков. Тесты сервисов используют транзакционную тестовую БД в памяти: проверяют одновременные команды, повторные награды, откат при ошибке сохранения и конкурентное изучение навыков. Отдельная команда `test:migrations` проверяет миграции на настоящем PostgreSQL: запуск с нуля, начальных героев, повторный запуск и сохранение изменённого прогресса. Адрес можно задать через `TEST_POSTGRES_URL`; используется отдельная временная база; пользователь PostgreSQL должен иметь право `CREATEDB` (в Docker оно уже есть). Обычные тесты не требуют PostgreSQL, MongoDB или Redis и дополнительно проверяют атомарность outbox и повторную доставку после отказа очереди. `test:infrastructure` создаёт отдельные временные PostgreSQL/MongoDB базы и уникальный Redis namespace, затем удаляет только их. Адреса можно задать через `TEST_POSTGRES_URL`, `TEST_MONGO_URL`, `TEST_REDIS_URL`. Проверка `pnpm check:architecture` запрещает обращения сервисов к драйверам, доступ к чужим репозиториям, сетевые запросы в UI-компонентах и циклические импорты.

Использованные официальные справочники: [NestJS gateways](https://docs.nestjs.com/websockets/gateways), [Kysely migrator](https://jsr.io/@kysely/kysely/doc/migration).
